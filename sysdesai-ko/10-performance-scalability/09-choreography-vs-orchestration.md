# Choreography vs Orchestration

> Source: https://www.sysdesai.com/learn/performance-scalability/choreography-vs-orchestration

---

## 서비스 조율 문제

마이크로서비스(Microservices) 아키텍처에서 비즈니스 프로세스는 종종 여러 서비스에 걸쳐 진행됩니다. 이커머스 주문을 처리하려면 주문 검증, 재고 예약, 결제 처리, 배송 스케줄링, 확인 이메일 발송이 필요합니다. 각 단계는 서로 다른 서비스에 존재합니다. 이를 어떻게 조율할까요? 근본적으로 다른 두 가지 답이 있습니다: **Choreography(코레오그래피)**와 **Orchestration(오케스트레이션)**.

## Choreography: 탈중앙화된 이벤트 기반 방식

**Choreography**에는 중앙 조율자가 없습니다. 각 서비스는 이벤트를 구독하고, 자신의 작업을 수행한 후 새로운 이벤트를 발행하여 반응합니다. 서비스들은 도메인 이벤트를 알고 있지만 서로를 알지 못합니다. 전체 워크플로는 독립적이고 이벤트 기반인 서비스들의 협력으로 자연스럽게 나타납니다 — 마치 안무가의 실시간 지시 없이 음악에 맞춰 춤추는 댄서들처럼.

Choreography: 각 서비스는 이벤트에 반응하고 자신의 이벤트를 발행하며, 중앙 조율자가 없음

- **느슨한 결합(Loose Coupling)**: 서비스들은 서로가 아닌 이벤트에 대해서만 알면 됩니다.
- **높은 확장성(High Scalability)**: 단일 병목 지점이 없으며, 각 서비스가 독립적으로 확장됩니다.
- **디버깅 어려움**: 전체 워크플로가 암묵적입니다 — 무슨 일이 일어났는지 파악하려면 서비스 간 이벤트를 추적해야 합니다.
- **분산 상태(Distributed State)**: 다중 서비스 프로세스의 현재 상태를 보여주는 단일 장소가 없습니다.
- **이벤트 증가**: 새 단계를 추가하려면 새 이벤트를 추가하고 기존 서비스들이 구독하도록 해야 합니다.

## Orchestration: 중앙화된 명령 기반 방식

**Orchestration**에서는 전용 **오케스트레이터(Orchestrator)** 서비스(또는 워크플로 엔진)가 전체 프로세스를 제어합니다. 각 서비스를 순차적(또는 병렬)으로 호출하고, 응답을 기다리며, 실패를 처리하고, 다음 단계를 결정합니다. 오케스트레이터는 프로세스 흐름에 대한 모든 비즈니스 로직을 보유합니다. 오케스트라를 지휘하는 지휘자와 같습니다.

Orchestration: 오케스트레이터가 워크플로를 단계별로 진행하며, 모든 조율 로직을 보유

- **명시적 워크플로**: 전체 프로세스 흐름이 오케스트레이터 한 곳에서 보입니다.
- **모니터링 용이**: 프로세스 상태가 중앙에서 관리되므로 대시보드 구성이 간단합니다.
- **오류 처리 용이**: 보상 트랜잭션(Compensating Transaction)과 재시도 로직이 오케스트레이터에 집중됩니다.
- **결합 위험**: 서비스들이 오케스트레이터의 API에 결합됩니다.
- **단일 장애점(Single Point of Failure)**: 오케스트레이터 자체가 고가용성을 보장해야 합니다.
- **확장성 병목**: 모든 조율 트래픽이 하나의 컴포넌트를 통해 흐릅니다.

## 비교표

| 항목 | Choreography | Orchestration |
| --- | --- | --- |
| 제어 모델 | 탈중앙화 (이벤트 기반) | 중앙화 (명령 기반) |
| 결합 방식 | 서비스 ↔ 이벤트만 결합 | 서비스 ↔ 오케스트레이터 API 결합 |
| 프로세스 가시성 | 암묵적 — 이벤트 추적 필요 | 명시적 — 오케스트레이터에서 확인 |
| 디버깅 | 어려움 — 분산 추적 필요 | 쉬움 — 단일 위치에서 확인 |
| 장애 처리 | 각 서비스가 자체 처리 | 오케스트레이터가 보상 처리 조율 |
| 확장성 | 각 서비스 독립 확장 | 오케스트레이터가 병목 될 수 있음 |
| 최적 사용처 | 단순하고 병렬적이며 느슨하게 결합된 흐름 | 장기 실행, 순차적, 복잡한 흐름 |

## 하이브리드 접근법

실제 시스템은 종종 두 가지를 혼합합니다. 일반적인 패턴: 고수준 비즈니스 프로세스(주문 생명주기)에는 오케스트레이터를 사용하고, 오케스트레이터의 각 단계 내부에서는 병렬 처리 가능한 하위 단계에 Choreography를 사용합니다. 예를 들어 오케스트레이터가 '배송 준비'를 트리거하고, 이행(fulfillment) 도메인 내에서 창고 서비스들이 이벤트를 통해 패키지를 조립하는 방식입니다.

**AWS Step Functions**, **Temporal**, **Conductor** 같은 워크플로 엔진은 내구성, 재시도, 시각화 기능이 내장된 오케스트레이션을 구현하여 오케스트레이터 인프라를 직접 구축할 필요를 없애줍니다.

> 📌
> 실제 사례: Uber의 Cadence/Temporal 기반 Orchestration
> Uber는 드라이버 온보딩, 트립 생명주기 관리, 결제 처리 같은 복잡한 워크플로를 오케스트레이션하기 위해 Cadence(현재 Temporal로 오픈소스화)를 구축했습니다. 각 워크플로는 내구성 있는 스테이트풀 오케스트레이션으로, 며칠 또는 몇 주 동안 실행될 수 있고, 프로세스 충돌에서도 살아남으며, 정확히 중단된 지점에서 재개할 수 있습니다. Uber가 Choreography 대신 Orchestration을 선택한 이유는 운영팀에게 프로세스 가시성과 보상 로직이 매우 중요했기 때문입니다.

## Saga 패턴과의 관계

**Saga 패턴**(2PC 없이 분산 트랜잭션 처리)은 Choreography 기반 또는 Orchestration 기반으로 구현할 수 있습니다. **Choreography Saga**는 이벤트를 발행하고 각 서비스가 순방향 동작 또는 보상 동작으로 반응하며, **Orchestration Saga**는 중앙 Saga 오케스트레이터가 순방향 단계를 명시적으로 호출하고, 실패 시 역순으로 보상 트랜잭션을 호출합니다.

> 💡
> 인터뷰 팁
> Choreography vs Orchestration은 다중 서비스 아키텍처를 제안한 후 가장 많이 나오는 후속 질문 중 하나입니다. 다음과 같이 구조화하세요: '서비스가 자연스럽게 이벤트 기반이고 최대한의 결합 해제를 원할 때 — 예를 들어 알림 사이드 이펙트에는 Choreography를 사용합니다. 비즈니스 프로세스에 복잡한 분기, 장기 실행 단계가 있거나 명시적인 보상 로직이 필요할 때 — 예를 들어 주문의 정확한 상태를 알아야 하는 체크아웃 흐름에는 Orchestration을 사용합니다.' 항상 하나만 선택하는 게 아니라 상황에 따라 적절히 선택할 줄 안다는 것을 보여주는 것이 면접관에게 인상을 줍니다.
