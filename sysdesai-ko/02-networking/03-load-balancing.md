# 부하 분산(Load Balancing): L4 vs L7

> Source: https://www.sysdesai.com/learn/networking/load-balancing

---

## 왜 부하 분산이 필요한가?

단일 서버는 처리 용량에 한계가 있습니다. 트래픽이 증가함에 따라 여러 백엔드 인스턴스로 요청을 분산해야 합니다. **부하 분산기(Load balancer)**는 서버군(Server fleet) 앞에 위치하여 들어오는 요청을 라우팅하며, 특정 서버에 부하가 집중되지 않도록 조절합니다. 또한 서버 장애 시 중복성(Redundancy)을 제공하고 수평 확장(Horizontal scaling)을 가능하게 합니다.

## L4 vs L7 부하 분산

부하 분산기는 **OSI 모델**의 서로 다른 계층에서 작동합니다. 가장 관련이 깊은 두 계층은 4계층(전송 계층)과 7계층(응용 계층)입니다.

| 측면 | L4 부하 분산기 | L7 부하 분산기 |
| --- | --- | --- |
| OSI 계층 | 전송 계층 (TCP/UDP) | 응용 계층 (HTTP/HTTPS/gRPC) |
| 인식 데이터 | IP 주소, 포트, TCP 연결 상태 | 전체 HTTP 헤더, URL 경로, 쿠키, 요청 본문 |
| 라우팅 기준 | IP + 포트만 사용 | URL 경로, 호스트네임, 헤더 값, HTTP 메서드 |
| TLS 종료 | 보통 지원하지 않음 (TLS 통과) | 지원 — TLS를 종료하고 백엔드에 재암호화 또는 평문 전송 |
| 성능 | 매우 빠름, 낮은 CPU 오버헤드 | 상대적으로 높은 CPU 부하(HTTP 파싱), 하지만 더 스마트한 라우팅 |
| 세션 고정 | IP 해시(IP-hash) 기반 | 쿠키(Cookie) 기반 (더 안정적) |
| 프로토콜 인지 | 없음 — 모든 TCP 트래픽을 동일하게 취급 | `/api`는 API 서버로, `/static`은 파일 서버로 라우팅 가능 |
| 예시 | AWS NLB, HAProxy TCP 모드, IPVS | AWS ALB, NGINX, Envoy, Traefik |

> 💡
> L4와 L7 중 선택 기준
> 단순한 처리량(초당 수백만 개의 짧은 TCP 연결, SMTP나 게임 서버와 같은 비 HTTP 프로토콜)이 중요할 때는 L4를 사용하세요. 콘텐츠 기반 라우팅, TLS 종료, 속도 제한(Rate limiting) 또는 HTTP 트래픽 가시성이 필요할 때는 L7을 사용하세요. 대부분의 현대적인 웹 애플리케이션은 L7 부하 분산기를 사용합니다.

## 부하 분산 알고리즘(Load Balancing Algorithms)

부하 분산기가 각 요청을 어떤 백엔드 서버로 보낼지 결정하는 방식은 **분산 알고리즘**에 의해 결정됩니다. 워크로드에 따라 적합한 알고리즘이 다릅니다.

| 알고리즘 | 작동 방식 | 적합한 사례 | 단점 |
| --- | --- | --- | --- |
| 라운드 로빈(Round-robin) | 서버 순서대로 순환하며 할당 | 동일한 사양의 서버, 균일한 요청 비용 | 서버 부하나 요청의 무게를 무시함 |
| 가중치 라운드 로빈(Weighted round-robin) | 라운드 로빈 방식이나 서버 가중치에 비례해 더 많은 요청을 할당 | 서로 다른 서버 사양(성능이 좋은 서버에 더 많이) | 여전히 실시간 부하를 반영하지 못함 |
| 최소 연결(Least connections) | 활성 연결 수가 가장 적은 서버로 라우팅 | 연결 시간이 긴 경우(WebSocket, 파일 업로드) | 연결 수가 실제 부하와 일치하지 않을 수 있음 |
| 최소 응답 시간(Least response time) | 평균 응답 시간이 가장 낮은 서버로 라우팅 | 지연 시간에 민감한 API | 활성 응답 시간 추적이 필요함 |
| IP 해시(IP hash) | 클라이언트 IP를 해싱하여 특정 서버에 고정 할당 | 세션 공유가 없는 상태 유지(Stateful) 서비스 | 부하가 불균형할 수 있음; 큰 NAT 풀(Pool)에서 비효율적 |
| 일관된 해싱(Consistent hashing) | 키(IP, 사용자 ID, URL)를 해시 링(Hash ring)에 매핑 | 캐시 효율적 라우팅, 상태 유지 서비스 | 서버 추가/삭제 시 리해싱이 필요함 |
| 무작위(Random) | 무작위로 백엔드 선택 | 단순함, 대규모 환경에서 의외로 잘 작동함 | 부하를 전혀 고려하지 않음 |

## 상태 확인(Health Checks)

부하 분산기는 백엔드 서버의 장애를 감지하기 위해 지속적으로 서버를 조사합니다. 상태가 나쁜(Unhealthy) 서버는 복구될 때까지 라우팅 대상에서 제외됩니다.

- **수동적 상태 확인(Passive health checks)**: 실제 트래픽에서 발생하는 오류를 모니터링합니다. 서버가 임계치를 넘는 5xx 오류나 TCP 리셋을 반환하면 비정상으로 간주합니다. 오버헤드는 없지만, 장애를 감지하기 위해 실제 트래픽 실패가 먼저 발생해야 합니다.
- **능동적 상태 확인(Active health checks)**: 부하 분산기가 주기적으로 가상 요청(HTTP GET `/health`, TCP 프로브 등)을 보내 예상된 응답이 오는지 확인합니다. 실제 트래픽에 영향을 주기 전에 장애를 감지할 수 있습니다.
- **상태 확인 파라미터**: 주기(조사 빈도), 타임아웃(대기 시간), 정상 임계치(정상으로 판단하기 위한 성공 횟수), 비정상 임계치(제외하기 위한 실패 횟수).

```yaml
# 예시: AWS ALB 타겟 그룹 상태 확인 설정
HealthCheckProtocol: HTTP
HealthCheckPath: /health
HealthCheckIntervalSeconds: 15
HealthCheckTimeoutSeconds: 5
HealthyThresholdCount: 2      # 2회 연속 성공 시 → 정상(Healthy)
UnhealthyThresholdCount: 3    # 3회 연속 실패 시 → 비정상(Unhealthy)
Matcher:
  HttpCode: "200"
```

## 세션 고정(Sticky Sessions / Session Affinity)

일부 애플리케이션은 세션 상태를 공유 저장소가 아닌 서버 메모리에 저장합니다. 세션 고정은 특정 클라이언트의 요청이 항상 동일한 백엔드 서버로 라우팅되도록 보장합니다.

- **IP 해시 기반 고정**: 동일한 클라이언트 IP의 모든 트래픽을 동일한 서버로 라우팅합니다. 대규모 NAT 풀(하나의 IP를 공유하는 많은 사용자)이나 IP가 자주 바뀌는 모바일 클라이언트 환경에서는 한계가 있습니다.
- **쿠키 기반 고정**: 부하 분산기가 첫 응답 시 쿠키(`AWSALB`, `JSESSIONID`)를 설정하고, 이후 요청에서 이를 사용하여 동일한 서버로 라우팅합니다. IP 해시 방식보다 더 안정적입니다.

> ⚠️
> 새로운 설계에서는 세션 고정을 피하세요.
> 세션 고정은 부하 재분산 능력을 떨어뜨리며(부하가 집중된 서버가 요청을 쳐낼 수 없음), 서버 재시작 시 장애를 유발합니다. 세션 상태를 외부 공유 저장소(Redis 등)로 분리하여 모든 서버가 어떤 요청이든 처리할 수 있는 무상태(Stateless) 아키텍처를 구축하는 것이 좋습니다.

## 연결 드레이닝(Connection Draining / Deregistration Delay)

배포나 스케일-인(Scale-in) 이벤트로 백엔드 서버를 제거할 때, 부하 분산기는 해당 서버에 대해 **연결 드레이닝** 모드로 들어갑니다. 이 모드에서는 새로운 요청은 보내지 않지만, 이미 진행 중인 요청이 유예 기간(보통 30~300초) 내에 완료될 수 있도록 허용합니다. 유예 기간이 지나면 남은 연결은 강제로 종료됩니다.

> 💡
> 면접 팁
> 클래식한 면접 질문: '요청 유실 없이 어떻게 서비스의 새 버전을 배포합니까?' 답은 연결 드레이닝과 롤링 배포(Rolling deployment) 전략을 조합하는 것입니다. 부하 분산기는 이전 서버를 우아하게 제거(연결 드레이닝)한 후 새 서버를 추가합니다. 새 서버군이 완전히 정상 상태가 된 후 부하 분산기에서 트래픽을 원자적으로 전환하는 블루/그린 배포까지 언급하면 가산점을 받을 수 있습니다.
