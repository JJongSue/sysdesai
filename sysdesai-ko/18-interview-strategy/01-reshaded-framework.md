# RESHADED 프레임워크

> Source: https://www.sysdesai.com/learn/interview-strategy/reshaded-framework

---

## 프레임워크가 필요한 이유

시스템 디자인 면접은 의도적으로 열린 형태입니다. 면접관은 "Twitter를 설계하세요" 또는 "알림 서비스를 만드세요"와 같은 모호한 지시를 주고, 여러분이 모호함을 구조로 분해하는 방식을 관찰합니다. 반복 가능한 프레임워크 없이는 대부분의 지원자가 방향 없이 횡설수설하거나, 문제에 합의하기 전에 구현 세부사항으로 직행합니다. 두 가지 패턴 모두 부실한 엔지니어링 판단력을 드러냅니다.

**RESHADED** 프레임워크는 면접관이 중요하게 생각하는 모든 차원을 올바른 순서로 다루도록 보장하는 일관된 멘탈 체크리스트를 제공합니다. 이는 **R**equirements(요구사항), **E**stimation(추정), **S**torage schema(저장소 스키마), **H**igh-level design(고수준 설계), **A**PI design(API 설계), **D**etailed design(상세 설계), **E**valuation(평가), **D**istinctive component(독특한 컴포넌트)를 나타냅니다.

> 💡
> 인터뷰 팁
> 모든 면접의 시작은 이렇게 말하세요: "체계적으로 접근하고 싶습니다 — 먼저 요구사항을 명확히 하고, 규모를 추정한 다음, 탑다운으로 설계하겠습니다. 괜찮으신가요?" 이것만으로도 구조적 사고를 즉시 신호하고 마음을 가다듬을 시간을 몇 초 벌 수 있습니다.

## RESHADED의 8단계

RESHADED 프레임워크 — 시스템 디자인 면접 답변의 8개 순차적 단계

### R — 요구사항(Requirements)

**기능 요구사항**(시스템이 무엇을 해야 하는가)과 **비기능 요구사항**(얼마나 잘 해야 하는가)을 분리하는 것으로 시작합니다. 범위를 확정하기 위한 명확한 질문을 합니다. 절대 가정하지 마세요 — 면접관들은 실제 엔지니어링 작업을 반영하는 스마트한 질문을 하는 지원자에게 좋은 점수를 줍니다.

| 기능 요구사항 | 비기능 요구사항 |
| --- | --- |
| 사용자가 트윗을 게시할 수 있음 | 99.99% 가용성 (연간 52분 다운타임) |
| 사용자가 다른 사용자를 팔로우할 수 있음 | 읽기는 p99에서 200ms 이내 반환 |
| 타임라인에 최신 트윗 표시 | 일간 활성 사용자 1억 명 처리 |
| 사용자가 좋아요 및 리트윗 가능 | 타임라인에 최종 일관성 허용 가능 |

> 💡
> 인터뷰 팁
> 명확화 질문을 3~5개의 핵심 질문으로 제한하세요. 규모(사용자가 몇 명인가?), 읽기/쓰기 비율(읽기 중심인가 쓰기 중심인가?), 일관성 요구사항(오래된 데이터가 허용되는가?), 그리고 명시적으로 범위 외의 기능에 대해 질문하세요. 이미 알아야 할 것들은 묻지 마세요.

### E — 추정(Estimation)

봉투 뒷면 계산(Back-of-the-Envelope)으로 설계를 현실에 기반합니다. **QPS**(초당 쿼리 수), **저장소** 요구사항, **대역폭** 필요량을 추정합니다. 이 수치들이 이후 모든 결정을 이끕니다 — 샤딩, 캐싱, CDN이 필요한지, 서버를 몇 대 프로비저닝해야 하는지.

> 📌
> 예시: Twitter 타임라인 추정
> 일간 활성 사용자 1억 명, 하루 5천만 건 트윗 게시 → ~580 쓰기/초. 하루 타임라인 읽기 요청 5억 건 → ~5,800 읽기/초. 읽기:쓰기 비율 ≈ 10:1 (읽기 중심). 평균 트윗 = 300바이트. 저장소: 하루 5천만 건 × 300바이트 = 하루 15GB → 트윗 텍스트만 연간 5.4TB (미디어 제외).

### S — 저장소 스키마(Storage Schema)

데이터베이스 유형(SQL vs NoSQL, 관계형 vs 문서형 vs 열 지향형 vs 그래프)을 선택하고 주요 데이터 모델을 정의합니다. 선택을 이끄는 **접근 패턴(Access Patterns)**을 설명합니다. 기본 키를 식별하고 핫스팟을 피하기 위한 샤딩 키를 어떻게 처리할지 파악합니다.

### H — 고수준 설계(High-Level Design)

시스템의 주요 컴포넌트를 화이트보드에 그립니다: 클라이언트, 로드 밸런서, 애플리케이션 서버, 데이터베이스, 캐시, CDN, 메시지 큐. 이 단계에서는 **서비스 경계 수준**에 머무르세요 — 내부 알고리즘을 아직 상세화하지 마세요. 더 깊이 들어가기 전에 면접관과 합의를 얻으세요.

### A — API 설계(API Design)

핵심 작업에 대한 공개 API 계약을 정의합니다. 엔드포인트, HTTP 메서드, 요청 파라미터, 응답 형태를 명시합니다. 좋은 API 설계는 서버 내부만이 아니라 클라이언트 경험에 대해 생각한다는 것을 보여줍니다.

```http
# 트윗 게시
POST /v1/tweets
Authorization: Bearer {token}
Content-Type: application/json

{
  "text": "Hello, world!",
  "media_ids": ["m_123", "m_456"]
}

# 응답
HTTP 201 Created
{
  "tweet_id": "t_789",
  "created_at": "2024-01-15T10:30:00Z",
  "author_id": "u_456"
}

# 홈 타임라인 조회
GET /v1/timeline?cursor={cursor}&limit=20
Authorization: Bearer {token}

# 응답
HTTP 200 OK
{
  "tweets": [...],
  "next_cursor": "eyJ0aW1lc3RhbXAiOiAxNzA1MzE0MjAwfQ=="
}
```

### D — 상세 설계(Detailed Design)

**가장 기술적으로 흥미로운 2~3개 컴포넌트**를 집중적으로 살펴봅니다. 면접관이 종종 여기서 방향을 제시할 것입니다 — 그 흐름을 따르세요. 팬아웃 전략, 샤딩 방식, 합의 알고리즘, 커스텀 데이터 구조에 대해 논의하는 단계입니다. 전체 그림을 잃지 않으면서 깊이를 보여주세요.

### E — 평가(Evaluation)

자신의 설계를 비판적으로 평가합니다. **장애 모드**(데이터베이스가 다운되면 어떻게 되나?), **병목**(어느 컴포넌트가 먼저 용량에 도달하나?), **트레이드오프**(성능을 위해 무엇을 희생했나?)를 식별합니다. 이 자기 평가는 엔지니어링 성숙도를 보여줍니다 — 훌륭한 엔지니어는 자신의 설계의 한계를 알고 있습니다.

> 💡
> 인터뷰 팁
> 이렇게 말해보세요: "제 설계를 스트레스 테스트해볼게요. 가장 약한 지점은 아마도 셀럽 쓰기 부하 하의 팬아웃 서비스일 것입니다. 팔로워가 1만 명 미만인 사용자는 쓰기 시점 팬아웃을, 셀럽은 읽기 시점 팬아웃을 받는 하이브리드 팬아웃 모델로 이를 해결하겠습니다." 약점을 선제적으로 식별하고 완화 방안을 제안하는 것은 시니어 레벨의 신호입니다.

### D — 독특한 컴포넌트(Distinctive Component)

모든 훌륭한 시스템 디자인 답변에는 "와우 모먼트"가 있습니다 — 눈에 띄게 더 깊이 들어가거나 비자명한 무언가를 제안하는 한 영역입니다. 영리한 샤딩 방식, 랭킹을 위한 특정 알고리즘, 특이한 캐싱 전략, 또는 공부한 실제 시스템의 신뢰성 패턴이 될 수 있습니다. 독특한 컴포넌트는 면접관이 면접 후에 기억하는 것입니다.

> 💡
> 좋은 독특한 컴포넌트의 조건
> 문제의 핵심 과제와 직접적으로 관련이 있어야 하고, 기술적으로 근거가 있어야 하며(막연하지 않게), 2~3분 안에 명확하게 설명할 수 있어야 합니다. 좋은 예시: Twitter의 셀럽을 위한 타임라인 캐시 사전 채우기, Chubby의 가상 노드를 사용한 Google의 일관된 해싱, 처리량을 위한 Kafka의 로그 구조 저장.

## RESHADED 한눈에 보기

| 단계 | 글자 | 핵심 산출물 | 시간 배분 |
| --- | --- | --- | --- |
| 요구사항 | R | 기능 + 비기능 목록, 범위 확정 | 5분 |
| 추정 | E | QPS, 저장소, 대역폭 수치 | 3분 |
| 저장소 스키마 | S | DB 선택 근거, 데이터 모델 스케치 | 3분 |
| 고수준 설계 | H | 컴포넌트 다이어그램, 데이터 흐름 그리기 | 7분 |
| API 설계 | A | 요청/응답이 있는 핵심 엔드포인트 정의 | 5분 |
| 상세 설계 | D | 2~3개 컴포넌트 심층 탐구 | 10분 |
| 평가 | E | 병목, 장애 모드, 트레이드오프 명시 | 4분 |
| 독특한 컴포넌트 | D | 한 가지 돋보이는 인사이트 또는 심층 탐구 | 3분 |
