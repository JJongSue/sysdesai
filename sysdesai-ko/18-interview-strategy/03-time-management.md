# 면접에서의 시간 관리

> Source: https://www.sysdesai.com/learn/interview-strategy/time-management

---

## 시간 관리가 신호인 이유

전체 시스템을 다루기 전에 시간이 소진되는 것은 시스템 디자인 면접에서 가장 흔한 실패 모드 중 하나입니다. 지원자가 데이터베이스 스키마에 35분을 쓰고 고수준 설계에 전혀 도달하지 못하면, 면접관은 그들이 규모에서 생각하는 능력을 평가할 수 없습니다. **시간 관리는 단순한 물류 문제가 아닙니다 — 엔지니어링 판단력의 신호입니다.**

시니어 엔지니어는 조사를 시간 박스화하고, 충분히 좋은 결정을 내리며, 앞으로 나아가는 방법을 알고 있습니다. SQL vs NoSQL 논쟁에 15분을 쓰는 것(둘 다 작동하는 경우)은 엄밀함이 아닌 분석 마비를 신호합니다.

> 💡
> 인터뷰 팁
> 모든 면접에 멘탈 시계를 가져가세요. 각 단계 후에 내부적으로 빠르게 체크하세요: "얼마나 사용했나? 얼마나 남았나? 속도가 맞나?" 뒤처지고 있다면, 명시적으로 범위를 좁히세요: "시간 관계상 먼저 해피 패스를 스케치하고 마지막에 엣지 케이스를 표시하겠습니다."

## 권장 시간 배분

면접은 일반적으로 35~45분 동안 진행됩니다. 아래 분배는 40분 세션을 기준으로 합니다. 다른 길이에는 비례적으로 조정하되 상대적 비중은 유지하세요.

| 단계 | 시간 | 면접 비율 | 목표 |
| --- | --- | --- | --- |
| 요구사항 + 명확화 | 5분 | 12% | 범위 확정, 기능 + 비기능 요구사항 |
| 추정 | 3분 | 7% | QPS, 저장소, 대역폭 — 설계를 이끄는 것만 |
| 저장소 스키마 | 3분 | 7% | DB 선택 + 주요 데이터 모델 |
| 고수준 설계 | 7분 | 17% | 전체 범위 훑기, 모든 주요 컴포넌트 그리기 |
| API 설계 | 5분 | 12% | 핵심 엔드포인트, 요청/응답 스케치 |
| 상세 설계 | 10분 | 25% | 두 컴포넌트 심층 탐구 |
| 평가 + 트레이드오프 | 5분 | 12% | 병목, 장애 모드, 대안 |
| 버퍼 / 질문 | 2분 | 5% | 마무리, 독특한 인사이트, 면접관 Q&A |

> ⚠️
> 가장 흔한 시간 낭비
> 1. 요구사항에 7분 이상 쓰기 (과도한 명확화). 2. 추정에 5분 이상 수학 계산하기. 3. 결정 없이 기술 선택 논쟁에 2~3분 이상 쓰기. 4. 하나의 컴포넌트에 너무 깊이 들어가서 나머지 시스템을 그리지 못하기.

## 다음으로 넘어갈 신호

현재 단계의 모든 세부사항을 소진했을 때가 아니라 **최소 실행 가능 출력**을 달성했을 때 다음 단계로 이동해야 합니다. 다음 "충분히 좋음" 신호를 알아차리는 법을 익히세요:

- **요구사항**: 기능 요구사항 3~5개, 비기능 요구사항 2~3개가 있고 면접관이 고개를 끄덕이거나 "좋네요"라고 말했습니다.
- **추정**: QPS 수치와 대략적인 저장소 수치가 있습니다. 이것들은 방향적으로 맞으면 됩니다, 정확할 필요는 없습니다.
- **고수준 설계**: 화이트보드에 모든 주요 컴포넌트가 레이블이 있는 연결과 함께 표현되었습니다. 고아 박스(연결되지 않은 박스)가 없습니다.
- **API 설계**: 2~3개의 가장 중요한 엔드포인트가 정의되었습니다. 모든 필드를 문서화할 필요는 없습니다.
- **상세 설계**: 하나의 컴포넌트에서 두 레벨 깊이 들어갔고 적어도 하나의 비자명한 설계 결정을 내렸습니다.

## 더 깊이 들어갈 때

면접관은 더 많은 깊이를 원할 때 신호를 보낼 것입니다. 주의할 사항: 같은 컴포넌트에 대한 반복 질문, "정확히 어떻게" 후속 질문, 또는 "데이터베이스 레이어에 대해 더 말씀해 주세요"와 같은 직접적인 요청. 이런 신호를 볼 때는 **전체 구조를 버리지 않고 나머지 시간을 해당 영역에 집중하세요**.

> 💡
> 인터뷰 팁
> 면접관이 특정 영역을 강하게 밀어붙이고 시간이 부족하다면, 명시적으로 시간을 교환할 수 있습니다: "이것이 분명히 중요합니다 — 제대로 다루고 싶습니다. API 설계 섹션을 건너뛰고 그 시간을 여기에 쓸까요?" 이것은 기피가 아닌 트레이드오프에 대한 판단력을 보여줍니다.

## 돌발 질문 처리하기

면접관은 때때로 면접 중간에 제약을 도입합니다: "데이터베이스가 1TB만 저장할 수 있다면?" 또는 "이제 실시간 협업을 추가하세요." 이런 돌발 질문들은 구조를 버리지 않고 압박 하에 적응할 수 있는지를 테스트합니다.

올바른 반응은 **구조적 적응**입니다: (1) 새 제약을 인정하고, (2) 어떤 컴포넌트에 영향을 주는지 식별하고, (3) 구체적인 변경을 제안하고, (4) 그것이 도입하는 트레이드오프를 언급합니다. 전체 설계를 재시작하지 마세요 — 영향받는 컴포넌트만 수술적으로 업데이트하세요.

> 📌
> 돌발 질문 처리 예시
>
> 돌발: "이제 시스템이 모바일에서 오프라인 모드를 지원해야 합니다."
> 좋은 반응: "흥미로운 제약입니다. 오프라인 지원은 세 가지에 영향을 미칩니다: 클라이언트에 로컬 우선 데이터 저장소(아마도 SQLite)가 필요하고, 연결이 재개될 때를 위한 동기화 프로토콜(CRDT 또는 벡터 클록을 사용한 Last-Write-Wins 사용), 그리고 API는 전체 상태 스냅샷이 아닌 변경 집합을 반환해야 합니다. 트레이드오프는 상당한 클라이언트 복잡성과 잠재적 병합 충돌입니다. 동기화 서비스를 표시하도록 아키텍처 다이어그램을 업데이트하겠습니다."

## 버퍼 시간 확보하기

항상 마지막 2~3분을 깔끔한 마무리와 면접관 질문을 위해 남겨두세요. 지원자가 여전히 설명 중인 상태로 시간이 다 되는 면접은 혼란스럽게 느껴집니다. 비록 설계가 불완전하더라도 깔끔한 마무리는 뒤죽박죽인 끝보다 더 좋은 인상을 남깁니다.

> 💡
> 인터뷰 팁
> 약 5분 남았을 때, 마음속으로 모드를 전환하세요: 새 아이디어 생성을 멈추고 **통합**을 시작하세요. 다룬 것 중 가장 중요한 2~3가지를 선택하고, 명확하게 요약하고, 더 시간이 있다면 다음에 할 것을 언급하고, 발언권을 넘기세요.
