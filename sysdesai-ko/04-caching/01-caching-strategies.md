# Caching Strategies: Write-Through, Write-Back, Write-Around (캐싱 전략: Write-Through, Write-Back, Write-Around)

> Source: https://www.sysdesai.com/learn/caching/caching-strategies

---

## Why Write Strategy Matters (쓰기 전략이 중요한 이유)

캐시는 원본 데이터(Source of Truth)와 얼마나 잘 동기화되느냐에 따라 그 가치가 결정됩니다. 캐시에서 데이터를 읽는 것은 간단합니다 — 데이터가 없으면(miss) 데이터베이스에서 가져와 캐시에 채우면 됩니다. **하지만 쓰는 것은 더 어렵습니다.** 데이터가 변경될 때마다 결정해야 합니다: 캐시를 먼저 업데이트할 것인가, 데이터베이스를 먼저 업데이트할 것인가, 아니면 캐시 업데이트를 아예 건너뛸 것인가? 이 답변이 시스템의 일관성, 쓰기 지연 시간(Write Latency), 그리고 데이터 손실 위험을 결정합니다.

쓰기를 처리하는 세 가지 근본적인 패턴이 있습니다: **Write-Through**, **Write-Back (Write-Behind)**, 그리고 **Write-Around**입니다. 각각 지연 시간, 일관성, 내구성 사이에서 서로 다른 트레이드오프를 가집니다. 잘못된 선택은 사용자에게 오래된(stale) 데이터를 제공하거나, 쓰기 증폭(write amplification)을 일으키거나, 아무도 읽지 않는 데이터로 캐시를 가득 채우는 결과를 초래할 수 있습니다.

## Write-Through

**Write-Through** 캐싱에서는 모든 쓰기가 캐시와 데이터베이스에 **동시에** (또는 순차적으로 캐시 먼저) 기록된 후 애플리케이션에 성공 응답을 보냅니다. 캐시는 항상 최근에 작성된 키에 대해 데이터베이스와 동일한 상태를 유지합니다.

**장점:** 읽기 요청 시 항상 최신의 일관된 캐시를 만날 수 있습니다. 이미 작성된 키에 대해 캐시가 오래된 데이터를 제공할 위험이 없습니다. 데이터가 데이터베이스에 동기적으로 저장되므로 캐시가 충돌하더라도 데이터 유실이 없습니다.

**단점:** 쓰기 지연 시간이 높습니다 — 애플리케이션이 캐시 쓰기와 데이터베이스 쓰기 모두를 기다려야 하기 때문입니다. 쓰기 집약적인 워크로드에서는 이 방식이 고통스러울 수 있습니다. 또한 모든 쓰기가 캐시를 오염시킬 수 있는데, 아무도 읽지 않을 데이터를 캐시에 기록하는 것은 낭비입니다 (캐시 미스 직후 발생하는 비싼 Write-Through 쓰기는 이중 낭비입니다).

📌
Best fit (적합한 경우)

Write-Through는 읽기 작업이 쓰기 작업보다 압도적으로 많고 강력한 읽기 일관성이 중요한 경우에 이상적입니다 — 예를 들어, 거의 모든 요청에서 읽히지만 변경은 드문 사용자 프로필 데이터, 설정값 또는 가격 정보 등이 해당됩니다.

## Write-Back (Write-Behind)

**Write-Back** (**Write-Behind**라고도 함) 캐싱에서는 애플리케이션이 **캐시에만** 데이터를 쓰고 즉시 성공 응답을 보냅니다. 캐시는 백그라운드에서 비동기적으로 변경된(dirty) 데이터를 데이터베이스에 기록합니다 — 타이머 기반, 캐시 축출(eviction) 시점 또는 배치(batch) 임계값 도달 시점에 기록이 발생합니다.

**장점:** 쓰기 지연 시간이 매우 낮습니다 — 데이터베이스가 크리티컬 패스(critical path)에 있지 않기 때문입니다. 쓰기 집약적인 워크로드에서는 여러 번의 쓰기를 하나의 데이터베이스 라운드 트립으로 합칠 수 있습니다 (예: 1,000번 증가한 카운터를 한 번의 `UPDATE`로 처리). 처리량이 매우 뛰어납니다.

**단점:** 데이터베이스에 기록되기 전에 캐시가 충돌하면 **데이터가 유실됩니다.** 따라서 내구성이 필요한 작업에는 부적합합니다. 또한 캐시와 데이터베이스가 일시적으로 불일치하는 구간이 생깁니다 — 다른 서비스가 데이터베이스에서 직접 읽을 경우 오래된 데이터를 보게 될 수 있습니다.

> ⚠️
> Durability risk (내구성 위험)
> Write-Back 캐시는 상태가 있는(stateful) 인프라로 다뤄야 합니다. Redis의 `appendonly yes` (AOF 지속성)를 사용하거나, 내구성이 보장된 메시지 브로커에 Write-Behind 큐를 유지하여 재시작 후에도 진행 중인 쓰기를 다시 실행할 수 있도록 해야 합니다.

📌
Best fit (적합한 경우)

Write-Back은 쓰기 작업이 많고 데이터 유실 위험이 어느 정도 허용되는 워크로드에 적합합니다: 조회수 카운터, 실시간 분석, 게임 리더보드 점수 또는 몇 초 정도의 데이터 유실이 허용되는 IoT 센서 원격 측정(telemetry) 등이 그 예입니다.

## Write-Around

**Write-Around** 캐싱에서는 쓰기 작업이 캐시를 완전히 우회하여 데이터베이스로 직접 전달됩니다. 캐시는 오직 캐시 미스 시에만 데이터가 채워집니다 (Lazy Loading / Cache-Aside 패턴). 이전에 캐싱된 값은 쓰기 작업 이후에 낡은 상태(stale)가 되며 다음 요청 시에만 갱신됩니다.

**장점:** 다시 읽히지 않을 일회성 쓰기 데이터로 캐시가 오염되는 것을 방지합니다. 이는 대량의 데이터 임포트 작업이나 자주 접근되지 않는 레코드에 특히 유용합니다. 자주 사용되는(hot) 데이터의 읽기는 여전히 캐시에서 처리됩니다.

**단점:** 쓰기 작업 이후 해당 키에 대한 첫 번째 읽기는 반드시 **Cache Miss(캐시 미스)**가 됩니다. 쓰기 직후 읽기가 자주 발생하는 사용자 대상 앱(예: 사용자가 프로필을 수정하고 즉시 확인하는 경우)에서는 데이터베이스에 읽기 부하가 집중될 수 있습니다.

## Strategy Comparison (전략 비교)

| Strategy(전략) | Write Latency(쓰기 지연) | Read Consistency(읽기 일관성) | Data Loss Risk(데이터 손실 위험) | Best For(용도) |
| --- | --- | --- | --- | --- |
| Write-Through | 높음 (동기 DB 쓰기) | 강함 (Strong) | 없음 (DB가 항상 최신) | 읽기 중심, 설정 데이터, 프로필 |
| Write-Back | 낮음 (비동기 DB 쓰기) | 최종적 (Eventual) | 캐시 충돌 시 발생 가능 | 쓰기 중심, 카운터, 분석 |
| Write-Around | 중간 (DB만 처리) | 최종적 (쓰기 후 미스) | 없음 | 일회성 쓰기, 대량 로드, 드문 읽기 |

## Cache-Aside (Lazy Loading) (캐시 어사이드)

**Cache-Aside** (Lazy Loading이라고도 함)는 가장 일반적인 **읽기** 전략이며 종종 Write-Around와 함께 사용됩니다. 애플리케이션이 먼저 캐시를 확인하고, 데이터가 없으면 데이터베이스에서 가져와 캐시에 저장합니다. 애플리케이션 코드가 직접 캐시 로직을 관리하며 프록시나 캐시 중계자는 관여하지 않습니다.

```python
def get_user(user_id: str) -> User:
    # 1. 캐시 확인
    cached = cache.get(f"user:{user_id}")
    if cached:
        return deserialize(cached)

    # 2. 캐시 미스 — DB에서 조회
    user = db.query("SELECT * FROM users WHERE id = ?", user_id)
    if not user:
        raise NotFoundError()

    # 3. TTL과 함께 캐시에 저장
    cache.set(f"user:{user_id}", serialize(user), ttl=300)
    return user
```

Cache-Aside는 탄력적입니다: 캐시가 다운되더라도 애플리케이션은 매번 데이터베이스에서 가져오면 됩니다 — 성능은 떨어지겠지만 서비스 중단은 없습니다. 단점은 **Cache Stampede(캐시 스탬피드)** 현상입니다: 콜드 스타트 직후나 캐시가 만료된 직후, 인기 있는 키에 대한 모든 요청이 동시에 데이터베이스로 몰릴 수 있습니다.

> 💡
> Interview Tip (인터뷰 팁)
> 면접관들은 거의 항상 캐싱 전략에 대해 묻습니다. Cache-Aside를 기본 읽기 패턴으로 먼저 제시한 다음, 읽기 일관성을 위해 Write-Through를 추가하거나 쓰기 처리량을 위해 Write-Back을 계층화하세요. 항상 본인이 선택한 트레이드오프를 언급하세요: "이것은 사용자 프로필 데이터이고 업데이트 후 오래된 데이터를 읽는 것이 나쁜 경험이 될 수 있으므로 여기서는 Write-Through를 사용하겠습니다." 트레이드오프를 명시적으로 언급하는 방식이 평범한 답변과 뛰어난 답변을 가르는 기준입니다.
