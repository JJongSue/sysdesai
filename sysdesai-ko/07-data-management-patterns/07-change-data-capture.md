# Change Data Capture (CDC, 변경 데이터 캡처)

> 출처: https://www.sysdesai.com/learn/data-management-patterns/change-data-capture

---

## Change Data Capture(CDC)란 무엇인가?

**Change Data Capture(CDC, 변경 데이터 캡처)**는 데이터베이스에서 발생하는 삽입(Inserts), 업데이트(Updates), 삭제(Deletes)와 같은 변경 사항을 감지하고 캡처하여, 이를 다운스트림 시스템에서 사용할 수 있는 이벤트 스트림으로 만드는 패턴입니다. 변경 사항을 확인하기 위해 데이터베이스를 폴링하는 대신, 데이터베이스 자체의 변경 피드를 관찰하므로 지연 시간이 짧고 오버헤드가 적습니다.

CDC는 이 모듈의 다른 많은 패턴을 뒷받침하는 인프라입니다. Transactional Outbox 릴레이가 아웃박스 삽입을 읽는 방법, CQRS 읽기 프로젝션을 최신 상태로 유지하는 방법, Elasticsearch 인덱스를 Postgres와 동기화하는 방법, 그리고 데이터 파이프라인이 데이터 웨어하우스로 변경 사항을 복제하는 방법 등이 모두 CDC를 통해 이루어집니다.

Debezium을 활용한 CDC: 데이터베이스의 변경 사항이 WAL에서 여러 다운스트림 컨슈머로 흐릅니다.

## CDC 구현 방식

| 방식 | 작동 방식 | 지연 시간 | 오버헤드 | 사용 시점 |
| --- | --- | --- | --- | --- |
| 로그 기반 CDC (Log-based CDC) | DB 트랜잭션 로그(WAL, binlog)를 읽음 | 1초 미만 | 매우 낮음 | 운영 시스템; 권장되는 방식 |
| 트리거 기반 CDC (Trigger-based) | DB 트리거가 변경 사항을 섀도 테이블에 기록 | 낮음 | 중간 정도의 쓰기 오버헤드 | 로그 접근이 불가능한 단순한 설정 |
| 쿼리 기반 폴링 | `SELECT WHERE updated_at > last_poll`을 주기적으로 실행 | 초~분 단위 | DB 쿼리 부하 발생 | 단순한 레거시 시스템; 제한적 사용 |
| 캡처를 포함한 이중 쓰기 | 애플리케이션이 DB와 이벤트 스트림 양쪽에 기록 | 없음 | 없음 (앱 내 로직) | DB 로그 접근이 불가능할 때 |

## Debezium: 실전에서의 로그 기반 CDC

**Debezium**은 가장 널리 사용되는 오픈 소스 CDC 플랫폼입니다. 데이터베이스 트랜잭션 로그를 추적하고 변경 이벤트를 Kafka 토픽에 발행하는 Kafka Connect 커넥터 세트로 실행됩니다. 각 행의 변경은 변경 전후의 상태, 작업 유형, 테이블 이름, 타임스탬프를 포함하는 구조화된 이벤트가 됩니다.

```json
// Postgres UPDATE에 대한 Debezium 변경 이벤트 예시
{
  "before": {
    "id": "order-123",
    "status": "pending",
    "total": 49.99
  },
  "after": {
    "id": "order-123",
    "status": "shipped",
    "total": 49.99
  },
  "op": "u",                    // "c"=생성, "u"=수정, "d"=삭제, "r"=읽기 (스냅샷)
  "ts_ms": 1708300800000,
  "source": {
    "db": "orders_db",
    "table": "orders",
    "txId": 789012,
    "lsn": 24567890           // Log Sequence Number — WAL 내 위치
  }
}
```

## CDC 활용 사례

-   **검색 인덱스 동기화** — Elasticsearch나 Solr 인덱스를 Postgres 소스 테이블과 최신 상태로 유지합니다. Postgres에서 제품이 업데이트되면 Debezium이 변경 사항을 발행하고, Kafka 컨슈머가 Elasticsearch 문서를 업데이트합니다.
-   **데이터 웨어하우스 ETL** — OLTP 데이터베이스 변경 사항을 데이터 웨어하우스(Snowflake, BigQuery)에 거의 실시간으로 복제하여, 느린 야간 배치 ETL 작업을 대체합니다.
-   **캐시 무효화 (Cache Invalidation)** — 소스 데이터가 변경되면 CDC 이벤트가 Redis의 캐시 제거(Eviction)를 트리거합니다. 이를 통해 고정된 TTL이 아니라 실제 데이터 변경 시점에 캐시가 무효화되도록 보장합니다.
-   **CQRS 읽기 모델 업데이트** — 쓰기 측 데이터베이스에서 CDC 이벤트를 소비하여 읽기 모델 프로젝션을 유지 관리합니다.
-   **마이크로서비스 데이터 복제** — 한 서비스의 데이터베이스 데이터를 다른 서비스의 로컬 복사본으로 복제하여 자율적인 쿼리가 가능하게 합니다.
-   **트랜잭셔널 아웃박스 릴레이** — 아웃박스 패턴의 전형적인 프로덕션 구현 방식입니다 (Debezium Outbox Connector).

## 초기 스냅샷 (Initial Snapshot) 처리

기존 데이터베이스에 처음 CDC를 설정할 때, 실시간 변경 사항을 스트리밍하기 전에 다운스트림 컨슈머를 기존 데이터로 채워야 합니다. Debezium은 **초기 스냅샷** 기능을 통해 이를 처리합니다. 실시간 WAL 스트리밍으로 전환하기 전에 모든 기존 행을 읽습니다(`read` 작업 이벤트 발행). 이 전환은 매끄럽게 이루어지며, 컨슈머는 과거 데이터를 마치 변경 이벤트인 것처럼 처리합니다.

> ℹ️
> CDC는 데이터베이스 설정이 필요합니다
> 로그 기반 CDC를 위해서는 특정 데이터베이스 설정이 필요합니다. Postgres의 경우 `wal_level = logical`이 필요하고, MySQL의 경우 `binlog_format = ROW`가 필요합니다. 이러한 설정은 데이터베이스 재시작이 필요할 수 있으며, 관리형 클라우드 데이터베이스에서는 항상 사용 가능하지 않을 수 있습니다. 아키텍처에서 이 방식을 채택하기 전에 항상 CDC 지원 여부를 확인하세요.

## 실제 활용 사례

**LinkedIn**은 Debezium의 모태가 된 Databus(내부 CDC 시스템)를 초기에 도입했습니다. **Airbnb**는 MySQL의 리스팅 데이터를 검색 인프라와 동기화하는 데 CDC를 사용합니다. **Shopify**는 Elasticsearch 상품 인덱스를 동기화 상태로 유지하는 데 CDC를 활용합니다. **Netflix**는 수백 개의 마이크로서비스 데이터베이스가 중앙 스트리밍 파이프라인으로 공급되는 데이터 메시(Data Mesh)를 위해 CDC를 사용합니다.

> 💡
> 인터뷰 팁
> 면접관이 '데이터베이스와 Elasticsearch 인덱스를 어떻게 동기화하나요?' 또는 '폴링 없이 읽기 모델을 어떻게 최신으로 유지하나요?'라고 물을 때 CDC는 정답이 될 수 있습니다. 데이터베이스의 트랜잭션 로그를 관찰하고 변경 사항을 이벤트로 발행한 다음, 해당 이벤트를 소비하여 다운스트림 저장소를 업데이트한다고 답변하세요. 사실상의 표준 도구인 Debezium을 언급하고, 데이터베이스 수준의 설정(예: Postgres의 논리적 복제)이 필요하다는 점을 덧붙이세요.
