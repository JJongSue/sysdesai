# Polyglot Persistence (폴리글랏 퍼시스턴스)

> 출처: https://www.sysdesai.com/learn/data-management-patterns/polyglot-persistence

---

## 모든 상황에 맞는 단 하나의 솔루션은 없습니다

**Polyglot persistence**(폴리글랏 퍼시스턴스, 다중 저장소 활용)는 하나의 시스템 내에서 여러 데이터베이스 기술을 사용하고, 각 기술을 해당 기술이 가장 잘 처리하는 접근 패턴(Access Pattern)에 맞춰 선택하는 관행입니다. 이 용어는 마이크로서비스 맥락에서 Martin Fowler와 Neal Ford에 의해 대중화되었으며, 서비스당 데이터베이스(Database per Service) 패턴을 통해 각 서비스가 자체 데이터 저장소를 자연스럽게 선택할 수 있게 되었습니다.

모든 면에서 뛰어난 단일 데이터베이스는 없습니다. 관계형 데이터베이스는 복잡한 관계를 가진 트랜잭션 주문 데이터에 적합합니다. 문서 데이터베이스는 스키마 유연성이 필요한 사용자 프로필에 더 좋습니다. 시계열 데이터베이스는 메트릭 데이터를 위해 특수 제작되었습니다. 그래프 데이터베이스는 사회적 연결의 탐색(Traversal)을 동등한 SQL 쿼리보다 수십 배 더 나은 성능으로 처리합니다. 폴리글랏 퍼시스턴스는 이러한 현실을 받아들입니다.

폴리글랏 퍼시스턴스: 하나의 시스템 내에서 서로 다른 데이터베이스가 서로 다른 데이터 접근 패턴을 처리합니다.

## 데이터베이스 선택 가이드

| 데이터베이스 유형 | 적합한 용도 | 예시 | 피해야 할 상황 |
| --- | --- | --- | --- |
| 관계형 (RDBMS) | ACID 트랜잭션, 복잡한 관계, 리포팅 | PostgreSQL, MySQL, CockroachDB | 스키마가 매우 유연해야 하거나 방대한 쓰기 처리량이 필요한 경우 |
| 문서 (Document) | 유연한 스키마, 중첩된 데이터, 카탈로그 | MongoDB, Firestore, CouchDB | 강력한 관계형 JOIN이 필요하거나 문서 간 ACID가 필요한 경우 |
| 키-값 (Key-Value) | 세션, 캐시, 속도 제한(Rate limiting), 기능 플래그 | Redis, DynamoDB, Memcached | 복잡한 쿼리나 관계가 필요한 경우 |
| 와이드 컬럼 (Wide-Column) | 높은 쓰기 처리량, 시계열, IoT | Cassandra, HBase, ScyllaDB | 무작위 접근 패턴이 자주 바뀌거나 애드혹(Ad-hoc) 쿼리가 필요한 경우 |
| 그래프 (Graph) | 소셜 그래프, 부정 탐지, 추천 | Neo4j, Amazon Neptune | 데이터가 본질적으로 그래프 형태가 아니거나 단순 쿼리가 주를 이룰 때 |
| 시계열 (Time-Series) | 메트릭, 로그, 시간순 이벤트 | InfluxDB, TimescaleDB, Prometheus | 데이터가 주로 시간순이 아니거나 업데이트가 빈번할 때 |
| 검색 엔진 (Search Engine) | 전체 텍스트 검색, 패싯 필터링, 지리 검색 | Elasticsearch, OpenSearch, Solr | 데이터의 원천(Source of Truth)으로 사용하거나 강력한 일관성이 필요할 때 |

## 데이터 동기화 (Data Synchronization)

폴리글랏 퍼시스턴스의 주요 과제는 여러 저장소 간의 데이터 일관성을 유지하는 것입니다. 데이터가 Postgres(신뢰할 수 있는 단일 원천)에 있지만 Elasticsearch에서도 검색이 가능해야 한다면, Postgres의 변경 사항이 Elasticsearch로 전파되어야 합니다. 이를 위한 주요 도구는 다음과 같습니다:

-   **CDC + Kafka** — Debezium이 Postgres의 WAL을 추적하여 변경 이벤트를 Kafka에 발행하고, 컨슈머가 Elasticsearch를 업데이트합니다. 거의 실시간 동기화를 위한 가장 권장되는 방식입니다.
-   **이중 쓰기 (Dual writes)** — 애플리케이션이 Postgres와 Elasticsearch 양쪽에 기록합니다. 단순하지만 이중 쓰기의 일관성 문제에 취약합니다. 강력한 재시도 및 조정 로직이 있을 때만 허용됩니다.
-   **예약된 배치 동기화 (Scheduled batch sync)** — 야간 작업 등을 통해 Postgres의 데이터를 내보내어 보조 저장소로 가져옵니다. 단순하지만 지연 시간이 길어 분석용이나 신선도 요구 사항이 낮은 시나리오에만 적합합니다.
-   **이벤트 기반 프로젝션 (Event-driven projection)** — CQRS 또는 이벤트 소싱 시스템에서 쓰기 저장소를 업데이트하는 동일한 이벤트를 소비하여 보조 저장소를 업데이트합니다.

## 운영 복잡성 (Operational Complexity)

> ⚠️
> 폴리글랏 퍼시스턴스는 운영 부담을 가중시킵니다
> 추가되는 각 데이터베이스 기술마다 팀은 해당 기술의 운영 모델을 배워야 합니다: 구성 방법, 모니터링, 백업, 확장, 그리고 장애 복구 방법 등을 익혀야 합니다. Postgres, Redis, MongoDB, Elasticsearch, Cassandra를 모두 운영한다는 것은 다섯 가지의 서로 다른 운영 가이드(Runbook)를 의미합니다. 신중하게 결정하세요. 새로운 기술 도입으로 얻는 이득이 운영 비용보다 확실히 클 때만 추가하세요.

## 실제 활용 사례

**Uber**가 대표적인 예입니다: 여정 데이터는 PostgreSQL(트랜잭션), 기사 위치는 맞춤형 지리 인덱싱 저장소, 로그는 Kafka + ELK, 기사 프로필은 Schemaless(문서 저장소), 배차 결정은 Riak을 사용합니다. **GitHub**은 관계형 데이터에 MySQL, 캐싱과 세션에 Redis, 코드 검색에 Elasticsearch, 데이터 분석에 HBase를 사용합니다. **Instagram**은 사용자 데이터와 관계에 Postgres, 대규모 피드에 Cassandra, 캐시에 Redis를 사용했습니다.

## 데이터베이스 추가 시점 선택 기준

-   접근 패턴이 현재 데이터베이스와 근본적으로 호환되지 않는가? (예: Postgres에서 전체 텍스트 검색은 가능하지만 대규모 환경에서는 효율적이지 않음)
-   기존 데이터베이스가 특정 워크로드에서 어려움을 겪고 있으며 인덱싱/샤딩(Sharding)으로 해결할 수 없는가?
-   데이터가 근본적으로 다른 생명주기를 가지고 있는가? (예: TTL 기반 보존이 필요한 시계열 메트릭)
-   팀이 운영 환경에서 새로운 기술을 관리할 준비가 되었는가?
