# Saga Pattern (사가 패턴): Choreography & Orchestration

> 출처: https://www.sysdesai.com/learn/data-management-patterns/saga-pattern

---

## 분산 트랜잭션이 어려운 이유

단일 데이터베이스를 사용하는 모놀리스(Monolith)에서는 트랜잭션이 쉽습니다. 작업을 `BEGIN/COMMIT`으로 감싸기만 하면 데이터베이스가 원자성(Atomicity)을 처리합니다. 하지만 서비스당 데이터베이스(Database per Service)를 사용하는 마이크로서비스에서는 이 방식이 작동하지 않습니다. 각 서비스는 자체 데이터베이스를 가지므로, 단일 트랜잭션이 모든 서비스를 아우를 수 없습니다. **2단계 커밋(Two-Phase Commit, 2PC)**이 고전적인 해결책이지만, 느리고 취약하며 모든 참여자가 가용한 상태여야 하므로 분산 시스템에서는 적합하지 않습니다.

**Saga 패턴**(사가 패턴)은 마이크로서비스의 대안입니다. 사가는 로컬 트랜잭션의 연속이며, 각 트랜잭션은 자체 서비스에서 실행됩니다. 만약 하나가 실패하면 이전에 완료된 트랜잭션들을 **보상 트랜잭션(Compensating Transactions)**을 통해 되돌리도록 조정됩니다. 분산 원자성 대신, 명시적인 롤백 로직을 통해 최종 일관성(Eventual Consistency)을 달성합니다.

## Choreography(코레오그래피) 기반 사가

**Choreography**(코레오그래피, 안무) 방식에는 중앙 조정자가 없습니다. 각 서비스는 이벤트를 수신 대기하고, 로컬 트랜잭션을 수행한 뒤 다음 이벤트를 발행함으로써 반응합니다. 서비스들은 완전히 분리되어 있으며, 서로에 대해 알지 못하고 오직 이벤트만 알고 있습니다.

코레오그래피 사가: 중앙 조정자 없이 서비스들이 이벤트에 반응합니다.

## 코레오그래피 실패 및 보상

단계가 실패하면(예: 결제 거절), 실패한 서비스는 실패 이벤트(`PaymentFailed`)를 발행합니다. 이전의 각 서비스는 실패 이벤트를 듣고 보상 트랜잭션을 실행합니다. 예를 들어 주문 서비스는 주문을 취소합니다. 재고가 아직 예약되지 않았다면 그곳에서는 보상이 필요하지 않습니다. 이 방식은 짧고 단순한 사가에는 잘 작동하지만, 복잡성이 증가하면 전체 흐름을 파악하기 어려워집니다.

## Orchestration(오케스트레이션) 기반 사가

**Orchestration**(오케스트레이션) 방식에서는 중앙의 **Saga Orchestrator**(사가 오케스트레이터, 프로세스 매니저 또는 사가 매니저라고도 함)가 각 서비스에 할 일을 명시적으로 지시합니다. 오케스트레이터는 사가가 어느 단계에 있는지 상태를 유지하며, API나 명령 메시지를 통해 서비스에 명령을 내립니다. 서비스는 성공 또는 실패로 응답하고, 오케스트레이터는 보상 트리거를 포함하여 다음에 무엇을 할지 결정합니다.

오케스트레이션 사가: 중앙 오케스트레이터가 각 단계를 명시적으로 조정합니다.

## Choreography vs Orchestration 비교

| 항목 | Choreography (코레오그래피) | Orchestration (오케스트레이션) |
| --- | --- | --- |
| 결합도 | 이벤트를 통해 서비스 간 느슨한 결합 | 서비스들이 오케스트레이터 인터페이스에 결합됨 |
| 가시성 | 전체 흐름 파악이 어려움 (여러 서비스에 분산됨) | 중앙에서 사가 상태를 쉽게 확인하고 추적 가능 |
| 복잡성 | 짧은 사가에는 단순하나, 길어지면 혼란스러움 | 초기 코드가 더 많지만, 복잡한 흐름으로 확장 가능 |
| 실패 처리 | 각 서비스가 보상에 대해 알고 있어야 함 | 오케스트레이터가 보상 로직을 중앙 집중화함 |
| 테스트 | 어려움 — 이벤트 체인을 시뮬레이션해야 함 | 쉬움 — 오케스트레이터 상태 머신을 직접 테스트 가능 |
| 도구 | Kafka, EventBridge | Temporal, AWS Step Functions, Axon |

## 보상 트랜잭션 (Compensating Transactions)

> ℹ️
> 보상은 롤백이 아닙니다
> 데이터베이스 롤백은 저장소 수준에서 변경 사항을 취소하는 것으로, 마치 작업이 일어나지 않았던 것처럼 만듭니다. 반면 보상 트랜잭션은 이전 작업을 논리적으로 취소하는 새로운 비즈니스 작업입니다. 예를 들어, 결제는 '롤백'될 수 없습니다. 이미 결제가 발생했기 때문입니다. 이때의 보상은 '환불'입니다. 보상 트랜잭션은 도메인에 명시적으로 설계되어야 하며, 자체적인 부수 효과(예: 환불 알림 이메일)를 가질 수 있습니다.

## 멱등성(Idempotency)의 필요성

사가의 각 단계는 실패 시 재시도될 수 있습니다. 사가에 참여하는 모든 서비스는 **멱등성(Idempotent)**을 갖춰야 합니다. 즉, 동일한 명령을 두 번 처리해도 한 번 처리한 것과 결과가 같아야 합니다. 표준적인 접근 방식은 사가 단계별로 고유한 멱등성 키(Idempotency Key)를 사용하고 이를 작업 결과와 함께 저장하는 것입니다.

## 실제 활용 사례

**Uber**는 **Temporal**(이전의 Cadence) 기반의 오케스트레이션 사가를 사용하여 기사, 가격, 매핑, 결제 서비스 간의 여정 이행(Trip fulfillment)을 조정합니다. **Netflix**는 콘텐츠 게시 워크플로우에 코레오그래피 기반 사가를 사용합니다. **Amazon**은 창고, 물류, 결제 마이크로서비스를 아우르는 주문 이행에 사가와 유사한 패턴을 사용합니다. **AWS Step Functions**는 관리형 사가 오케스트레이터 서비스를 제공합니다.

> 💡
> 인터뷰 팁
> 사가 패턴은 거의 모든 마이크로서비스 인터뷰에서 등장합니다. 분산 시스템에서 왜 2PC가 작동하지 않는지(블로킹 문제, 참여자 가용성 등) 설명하며 시작하세요. 그런 다음 두 가지 접근 방식을 제시하세요. 단계가 적고 단순한 흐름에는 코레오그래피를, 가시성이 중요한 복잡한 흐름에는 오케스트레이션을 추천하세요. 보상 트랜잭션과 멱등성을 언급하는 것을 잊지 마세요. 이는 단순히 정상 경로(Happy path)뿐만 아니라 실제 운영 환경의 현실을 이해하고 있음을 보여줍니다.
