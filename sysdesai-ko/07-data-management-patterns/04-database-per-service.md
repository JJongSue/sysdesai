# Database per Service (서비스당 데이터베이스)

> 출처: https://www.sysdesai.com/learn/data-management-patterns/database-per-service

---

## 원칙

**Database per Service**(서비스당 데이터베이스)는 마이크로서비스의 기초가 되는 패턴입니다. 각 서비스는 자체 데이터 저장소를 소유하고 독점적으로 관리합니다. 다른 어떤 서비스도 해당 데이터베이스에 직접 쿼리하거나 쓸 수 없으며, 접근은 오직 서비스의 API를 통해서만 가능합니다. 이는 마이크로서비스가 코드 수준에서 강제하는 서비스 격리에 대응하는 데이터 격리 방식입니다.

이 패턴이 없다면 공유 데이터베이스(Shared database)는 강력한 결합 지점이 됩니다. 한 팀의 스키마(Schema) 변경이 다른 팀의 시스템을 중단시키고, 데이터베이스 병목 현상이 모든 서비스에 영향을 미치며, 각 워크로드에 맞는 적절한 데이터베이스 기술을 독립적으로 선택할 수 없게 됩니다. 마이크로서비스의 핵심 약속인 독립적인 배포 및 확장성이 무너지는 것입니다.

공유 데이터베이스는 결합을 생성하지만(안티 패턴), 서비스당 데이터베이스 패턴은 각 서비스가 자체 저장소를 소유하게 합니다.

## Isolation Levels (격리 수준)

마이크로서비스에서의 데이터베이스 격리는 스펙트럼 상에 존재합니다. 조직의 성숙도와 배포 모델에 맞는 수준을 선택하세요.

| 격리 수준 | 방식 | 장점 | 단점 |
| --- | --- | --- | --- |
| 별도의 DB 인스턴스 | 각 서비스가 자체 DB 서버를 실행 | 완전한 격리, 서로 다른 DB 기술 사용 가능 | 운영 오버헤드가 가장 높음 |
| 별도의 데이터베이스/스키마 | 동일한 DB 클러스터, 서비스별 별도 스키마 | 논리적 격리, 운영이 단순함 | 자원 경합(Resource contention) 가능성 |
| 별도의 테이블 접두사 | 동일한 스키마, `order_*`, `user_*` 식의 테이블명 | 운영상 가장 쉬움 | 가장 약한 격리, 실수로 데이터를 공유하기 쉬움 |

## 서비스 간 쿼리 (Cross-Service Queries)

서비스당 데이터베이스 패턴에 대한 가장 흔한 반론은 '여러 서비스에 걸친 데이터를 어떻게 JOIN하는가?'입니다. 예를 들어 주문 페이지에는 사용자 이름(사용자 서비스)과 재고 상태(재고 서비스)가 필요합니다. 공유 데이터베이스에서는 세 테이블 JOIN으로 해결되지만, 데이터베이스가 분리되면 JOIN을 할 수 없습니다.

해결 방법은 다음과 같습니다:

1.  **API Composition (API 조합)** — API Gateway나 전용 집계 서비스가 여러 서비스를 호출하고 애플리케이션 코드에서 결과를 조합합니다. 단순하고 동기적이지만 지연 시간(Latency)이 추가됩니다.
2.  **CQRS Read Model (읽기 모델)** — 프로젝터가 여러 서비스의 이벤트를 구독하고, 쿼리에 필요한 모든 데이터를 이미 가지고 있는 비정규화된 읽기 모델을 구축합니다. 자주 접근하는 집계 보기에 가장 적합합니다.
3.  **이벤트를 통한 데이터 복제** — 서비스는 데이터가 변경될 때 이벤트를 발행합니다. 다른 서비스들은 필요한 데이터의 로컬 복사본을 유지합니다. 최종 일관성(Eventual consistency)을 가지며, 쿼리 시점에 서비스 간 호출이 필요 없습니다.

API Composition 패턴: 게이트웨이가 여러 서비스를 호출하고 메모리에서 결과를 병합합니다.

## 데이터 중복의 트레이드오프

> ⚠️
> 데이터 중복은 버그가 아니라 기능입니다
> 서비스가 다른 서비스로부터 필요한 데이터를 복제할 때(예: 주문 서비스가 주문 시점의 고객 이름 스냅샷을 저장하는 경우), 이는 의도된 것입니다. 이를 통해 주문 서비스는 자율성을 갖게 되며, 사용자 서비스가 다운되더라도 작동할 수 있습니다. 트레이드오프는 사용자 서비스의 업데이트가 이벤트를 통해 전파되어야 한다는 점이며, 이전 주문들은 과거의 이름을 유지하게 됩니다. 이는 종종 올바른 비즈니스 동작이기도 합니다.

## 마이그레이션 전략

공유 모놀리식 데이터베이스에서 서비스당 데이터베이스로 전환하는 것은 마이크로서비스 전환에서 가장 어려운 부분 중 하나입니다. **Strangler Fig**(교살자 무화과) 접근 방식이 효과적입니다. 서비스 경계를 식별하고, 해당 서비스의 테이블을 새 데이터베이스로 추출한 다음, Transactional Outbox(또는 CDC)를 사용하여 전환 기간 동안 데이터를 동기화된 상태로 유지합니다. 쿼리를 새 서비스 API로 전환한 후 기존 공유 테이블을 제거합니다.

> 💡
> 인터뷰 팁
> 인터뷰에서 서비스당 데이터베이스를 논의할 때, 서비스 간 쿼리 문제를 먼저 언급하세요. 면접관이 반드시 물어볼 것입니다. 단순한 경우에는 API Composition을, 복잡한 집계에는 CQRS 읽기 모델을 제시하세요. 또한 이 패턴이 다중 언어 저장소(Polyglot Persistence)를 가능하게 한다는 점도 언급하세요. 각 서비스가 접근 패턴에 가장 적합한 DB 기술을 사용할 수 있습니다(예: 추천 서비스는 Graph DB를 사용하고 주문 서비스는 Postgres를 사용).
