# Priority Queue 패턴

> Source: https://www.sysdesai.com/learn/reliability-resilience/priority-queue

---

## 우선순위가 중요한 이유

모든 작업이 동일한 것은 아닙니다. 결제 확인 이메일은 주간 뉴스레터보다 더 시급합니다. 프리미엄 고객의 내보내기 작업은 무료 티어 사용자의 대량 작업 뒤에서 기다려서는 안 됩니다. **Priority Queue 패턴**은 큐에 백로그가 있더라도 우선순위가 높은 메시지가 낮은 메시지보다 먼저 처리되도록 보장합니다.

## 구현 접근 방식

| 접근 방식 | 동작 방식 | 장점 | 단점 |
| --- | --- | --- | --- |
| 네이티브 우선순위 큐 | 브로커가 메시지의 우선순위 필드를 지원; 높은 우선순위가 먼저 전달됨 | 단순함, 단일 큐 | 지원하는 브로커가 적음 (RabbitMQ 지원; SQS, Kafka 미지원) |
| 우선순위별 별도 큐 | N개의 큐(상, 중, 하); 소비자가 상위 큐부터 먼저 확인 | 모든 브로커에서 작동; 명확한 분리 | 소비자 로직이 복잡해짐; 소비자 공유가 어려움 |
| 가중치 기반 소비자 | 높은 우선순위 큐에 더 많은 소비자 인스턴스를 할당 | 절대적 우선순위가 아닌 처리량 가중치 방식 | 낮은 우선순위도 여전히 처리량을 가짐; SLA 미충족 가능성 |
| 별도 워커 풀이 있는 우선순위 레인 | 큐 티어별 전용 소비자; 상위 우선순위 풀이 더 큼 | 강력한 격리; 티어별 예측 가능한 SLA | 별도 풀 운영에 따른 리소스 오버헤드 |

## 우선순위별 별도 큐 (가장 일반적)

소비자는 높은 우선순위 큐를 먼저 폴링합니다; 비어 있는 경우에만 중간, 그 다음 낮은 우선순위를 확인합니다.

각 소비자는 HIGH 큐를 먼저 확인하는 폴링 루프를 구현합니다. 비어 있을 때만 MEDIUM을 확인하고, 그 다음 LOW를 확인합니다. 이는 소비자가 높은 우선순위 항목만 처리하느라 완전히 포화되지 않는 한, 높은 우선순위 작업이 낮은 우선순위 작업 뒤에서 기다리지 않도록 보장합니다.

typescript

```
async function pollWithPriority(
  queues: { high: Queue; medium: Queue; low: Queue }
) {
  while (true) {
    // 높은 우선순위 먼저 확인
    let msg = await queues.high.receive({ waitTimeSeconds: 0 });

    // HIGH가 비어 있으면 MEDIUM으로 넘어감
    if (!msg) {
      msg = await queues.medium.receive({ waitTimeSeconds: 0 });
    }

    // MEDIUM도 비어 있으면 LOW로 넘어감
    if (!msg) {
      msg = await queues.low.receive({ waitTimeSeconds: 20 }); // long-poll
    }

    if (msg) {
      await processMessage(msg);
      await msg.queue.acknowledge(msg.receiptHandle);
    }
  }
}
```

## 기아 상태 방지 (Preventing Starvation)

HIGH 큐가 항상 차 있다면, LOW 우선순위 메시지는 무기한 **기아 상태(starve)**에 빠질 수 있습니다. 이를 방지하기 위한 전략:

1. **에이징 기반 승급(Age-based promotion)** — 메시지가 대기한 시간을 추적하여, 최대 대기 시간이 지나면 더 높은 우선순위 큐로 승급시킵니다 (예: 10분 이상 된 LOW 메시지를 MEDIUM으로 변경).
2. **가중치 기반 폴링(Weighted polling)** — 무조건 상위 큐만 확인하는 대신, 높은 우선순위 N개당 낮은 우선순위 1개를 처리하도록 설정합니다.
3. **용량 예약(Capacity reservation)** — 상위 큐의 깊이와 상관없이 기간당 최소 K번의 소비자 사이클을 하위 우선순위 큐에 할당합니다.
4. **SLA 모니터링** — 하위 우선순위 큐의 깊이나 대기 시간이 임계값을 초과할 때 알람을 울려 긴급 용량 확장을 트리거합니다.

## RabbitMQ 네이티브 우선순위 지원

RabbitMQ는 `x-max-priority` 큐 인수를 통해 네이티브 우선순위 큐를 지원합니다(1–255). 메시지는 `priority` 속성을 가지며, 우선순위가 높은 메시지가 먼저 디큐(dequeue)됩니다. 브로커는 내부적으로 우선순위 수준별로 별도의 서브 큐를 유지합니다. 단순한 경우에는 편리하지만 한계가 있습니다: 우선순위는 메시지 유형이 아닌 메시지별로 지정되며, 최대 우선순위 값이 매우 높으면 메모리 오버헤드가 증가합니다.

> ℹ️
> Kafka는 메시지 우선순위를 지원하지 않습니다.
> Kafka는 우선순위 큐가 아닌 로그(log)입니다. 파티션 내의 메시지는 항상 오프셋(offset) 순서대로 전달됩니다. Kafka에서 우선순위를 구현하려면 우선순위 티어별로 별도의 토픽(topic)을 사용하고 전용 소비자 그룹을 운영해야 합니다. 애플리케이션 로직에서 높은 우선순위 토픽을 먼저 소비하도록 구현하세요.

> 💡
> 인터뷰 팁
> 우선순위 큐 질문은 알림 시스템, 작업 스케줄러 또는 고객 지원 티켓팅 설계 맥락에서 자주 나옵니다. 우선순위를 할당하는 방법(사용자 티어, 메시지 유형, 비즈니스 중요도), 기아(starvation) 위험 및 이를 완화하기 위한 에이징 기반 승급, 그리고 SLA 목표를 달성하기 위해 우선순위 티어별 큐 지연 시간(lag)을 모니터링하는 방법에 대해 논의하세요.
