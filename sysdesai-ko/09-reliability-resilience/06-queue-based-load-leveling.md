# Queue-Based Load Leveling

> Source: https://www.sysdesai.com/learn/reliability-resilience/queue-based-load-leveling

---

## 부하 스파이크 문제 (The Load Spike Problem)

대부분의 서비스는 트래픽이 몰리는 burst를 겪습니다: 반짝 세일(flash sale), 예정된 작업, 일과 종료 시점의 리포트, 또는 갑작스러운 바이럴 이벤트 등입니다. 서비스가 모든 요청을 피크 타임 속도에 맞춰 동기적으로 처리해야 한다면, 피크에 맞춰 리소스를 할당해야 하므로 유휴 시간에는 용량이 낭비됩니다. 반대로 충분하지 않으면 마비되어 실패하게 됩니다. **Queue-based load leveling**은 메시지 큐를 버퍼로 사용하여 생산 속도(production rate)와 소비 속도(consumption rate)를 분리합니다.

생산자(producer)는 피크 속도로 작업 항목을 큐에 넣고, 소비자(consumer)는 안정적이고 지속 가능한 속도로 이를 처리합니다. 큐는 그 차이를 흡수하여, 레이턴시 스파이크를 burst가 가라앉으면 해소될 일시적인 백로그(backlog)로 변환합니다.

## 아키텍처 (Architecture)

버퍼로서의 큐: 생산자는 피크 속도로 밀어넣고, 작업자는 지속 가능한 속도로 가져옴

## 장점

- **트래픽 스파이크 완화(Smooths traffic spikes)** — 큐가 burst를 흡수하므로 작업자가 결코 과부하되지 않습니다.
- **독립적 확장(Independent scaling)** — 생산자와 소비자는 각자의 로드 프로필에 따라 독립적으로 확장할 수 있습니다.
- **결함 허용(Fault tolerance)** — 작업자가 다운되더라도 메시지는 큐에 남아 있으며 다른 작업자에 의해 재처리됩니다.
- **디커플링(Decoupling)** — 생산자는 소비자에 대해 알 필요가 없으며, 생산자를 변경하지 않고도 소비자 구현을 교체할 수 있습니다.
- **비용 최적화(Cost optimization)** — 소비자 집합의 크기를 피크 부하가 아닌 평균 부하에 맞춰 적절히 설정할 수 있습니다.

## 백프레셔 (Backpressure)

큐는 무한하지 않습니다. 큐의 깊이(depth)가 임계값을 넘어가면, **백프레셔(backpressure)**를 통해 상위 단계에 속도를 늦추라고 신호를 보냅니다. 구현 방식은 다음과 같습니다: (1) **생산자 블로킹(blocking producers)** — 큐가 가득 찼을 때 `send()` 호출을 차단합니다. (2) **드롭(dropping)** — 큐가 가득 찼을 때 새로운 메시지를 버립니다 (중요하지 않은 메트릭에 적합). (3) **Rate limiting** — 큐 깊이가 임계값을 초과할 때 API gateway가 생산자를 제한합니다. (4) **소비자 풀 확장(expanding consumer pool)** — 큐 깊이에 따라 작업자를 자동 확장합니다.

> ⚠️
> 무제한 큐는 위험합니다.
> 제한 없이 늘어나는 무제한 큐는 결국 메모리를 고갈시켜 브로커나 애플리케이션을 중단시킵니다. 항상 최대 큐 깊이를 설정하고, 큐가 가득 찼을 때 차단할지, 버릴지, 확장할지를 명시적으로 결정하세요. 큐 깊이를 핵심 운영 메트릭으로 모니터링하세요.

## 시퀀스: 스파이크 흡수 (Sequence: Spike Absorption)

큐가 스파이크를 흡수합니다. 작업자는 일정한 속도로 처리하며 결국 백로그를 비웁니다.

## Load Leveling을 위한 큐 선택

| 큐 | 적합한 용도 | 주요 특징 |
| --- | --- | --- |
| Amazon SQS | 단순 작업 큐, AWS 네이티브 | 무한 확장, 관리형, at-least-once |
| RabbitMQ | 복잡한 라우팅, 승인(acknowledgment) 제어 | Exchanges, DLQ, 우선순위 지원 |
| Apache Kafka | 높은 처리량, 재실행 필요, 이벤트 스트리밍 | 로그 보관, consumer groups, 순서 보장 |
| Azure Service Bus | 엔터프라이즈 메시징, 세션, 순서 보장 | FIFO 세션, 트랜잭션 |

> 💡
> 인터뷰 팁
> 설계 면접에서 '트래픽 스파이크 처리' 요청을 받으면 즉시 queue-based load leveling을 언급하세요. 큐 깊이 모니터링, 소비자 자동 확장(예: ASG를 구동하는 SQS 큐 깊이 메트릭), 그리고 큐가 가득 찼을 때의 처리(백프레셔 또는 드롭)에 대해 논의하세요. 트레이드오프도 언급하세요: 동기식 API는 즉각적인 피드백을 주지만, 큐 방식은 응답을 비동기식으로 만듭니다(결과를 확인하기 위해 콜백, 폴링 또는 웹소켓이 필요함).

## 동기식 처리와의 트레이드오프

Queue-based load leveling은 **레이턴시**를 유발합니다. 요청이 즉시 처리되지 않기 때문입니다. 즉각적인 응답이 필요한 유스케이스(예: 결과를 반환하는 API 호출)에는 부적합합니다. fire-and-forget 작업(이메일 발송, 리포트 생성, 이미지 크기 조정, 비동기 결제 처리)에는 큐가 올바른 선택입니다. 하이브리드 설계에서는 작업 ID와 함께 즉시 `202 Accepted`를 반환하고, 클라이언트가 완료 시 웹훅을 받거나 폴링하게 합니다.
