## 문제 정의

알림 시스템은 다른 서비스의 이벤트를 기반으로 사용자에게 여러 채널 — **푸시 알림**(모바일/데스크톱), **이메일**, **SMS**, **인앱** — 으로 메시지를 전달합니다. 과제는: 올바른 채널로 라우팅하기, 사용자 설정 존중하기, 서드파티 전달 실패를 우아하게 처리하기, 사용자를 스팸으로 괴롭히지 않기(속도 제한)입니다. 대규모에서 Facebook과 같은 시스템은 하루에 수십억 건의 알림을 처리합니다.

## 요구 사항

| 기능 요구 사항 | 비기능 요구 사항 |
| --- | --- |
| 푸시, 이메일, SMS, 인앱 알림 전송 | 하루 10억 건 알림 |
| 사용자 설정 관리 (채널 및 유형별 옵트인/옵트아웃) | 중요 알림은 5초 이내 전달 |
| 변수 치환이 있는 템플릿 기반 메시지 | 최소 1회 전달 보장 |
| 우선순위 레벨: 중요, 높음, 보통, 낮음 | 99.9% 전달 성공률 |
| 전달 상태 추적 및 실패 시 재시도 | 사용자에게 중복 알림 없음 |
| 예약 알림 | 속도 제한: 사용자당 시간당 최대 10건 푸시 |

## 사용자 설정(User Preferences)

모든 알림은 사용자 설정을 존중해야 합니다. 설정 매트릭스는 `(userId, notificationType, channel)` → `enabled`를 매핑합니다. 내구성을 위해 MySQL에 저장되고 낮은 지연 조회를 위해 Redis에 캐시됩니다. 예시 스키마:

```sql
CREATE TABLE notification_preferences (
  user_id    BIGINT NOT NULL,
  notif_type VARCHAR(64) NOT NULL,   -- 예: 'order_update', 'marketing', 'chat'
  channel    VARCHAR(16) NOT NULL,   -- 'push', 'email', 'sms', 'in_app'
  enabled    BOOLEAN DEFAULT TRUE,
  updated_at TIMESTAMP DEFAULT NOW(),
  PRIMARY KEY (user_id, notif_type, channel)
);

-- 캐시 키 패턴: prefs:{userId}:{notif_type} → 채널 플래그의 JSON 블롭
-- TTL: 5분 (사용자 변경은 최종 일관성)
```

## 우선순위 큐와 속도 제한

모든 알림이 동등하지 않습니다. **우선순위별로 별도의 Kafka 토픽** 사용: `notif.critical`, `notif.high`, `notif.normal`, `notif.low`. 워커는 토픽 그룹에 할당되며 중요 토픽에 컨슈머가 가장 많습니다. 속도 제한으로 알림 피로를 방지합니다:

- **사용자별 속도 제한**: 사용자당 시간당 최대 10건 푸시 알림 (Redis의 토큰 버킷).
- **마케팅 vs 트랜잭션**: 트랜잭션 알림(주문 확인, 결제 실패)은 속도 제한을 우회; 마케팅은 속도 제한 적용.
- **방해 금지 시간(Quiet Hours)**: 사용자 시간대 존중 — 사용자가 설정한 방해 금지 시간(예: 오후 11시~오전 7시) 동안 비중요 알림 억제.
- **중복 제거**: 각 알림에 `notifId`(UUID) 할당; 전송 전 Redis에서 중복 여부 확인. TTL: 24시간.

## 재시도와 Dead Letter Queue (DLQ)

서드파티 프로바이더(FCM, Twilio)는 일시적으로 실패할 수 있습니다. **지수 백오프 재시도**를 상한과 함께 구현하세요 (예: 3회 시도: 즉시, 1분, 5분). 모든 재시도 소진 후 모니터링 및 수동 검사를 위해 **DLQ**로 전송합니다. DLQ 깊이가 임계값을 초과하면 알림을 발생시킵니다.

> ⚠️
> 멱등성이 매우 중요합니다
> Kafka의 최소 1회 전달 시맨틱으로 인해 알림 워커가 동일한 이벤트를 두 번 처리할 수 있습니다. 중복 제거 없이는 사용자가 중복 알림을 받게 됩니다. 전송 전에 항상 단기 Redis 키(`notif:{notifId}:sent`)를 확인하세요. `SET NX EX 86400`으로 하나의 작업에서 원자적으로 확인 및 설정합니다.

## 템플릿 시스템

알림 내용은 변수 치환이 있는 템플릿으로 구성됩니다. 템플릿은 데이터베이스(MySQL)에 저장되고 Redis에 캐시됩니다. 주문 확인 예시 템플릿:

```text
템플릿 ID: order_confirmed_push
채널: push
제목: "주문이 확인되었습니다!"
본문: "안녕하세요 {{firstName}}님, 주문 #{{orderId}}가 확인되었습니다.
       예상 배송일: {{deliveryDate}}."

런타임 렌더링:
  variables = { firstName: "길동", orderId: "ORD-12345", deliveryDate: "2월 22일" }
  rendered  = "안녕하세요 길동님, 주문 #ORD-12345가 확인되었습니다.
               예상 배송일: 2월 22일."
```

## 확장성 고려 사항

- **Kafka 파티셔닝**: `notif.normal`을 `userId`로 파티셔닝하여 사용자별 순서를 유지하고 여러 워커가 동시에 같은 사용자를 처리하지 않도록 합니다 (중복 전송 방지).
- **워커 오토스케일링**: Kafka 컨슈머 랙(Lag)을 기반으로 워커를 확장합니다. 랙 > 10K 메시지 → 워커 추가. 중요 토픽은 항상 최소 N명의 워커 유지.
- **서드파티 API 연결 풀링**: FCM과 SES에는 연결 제한이 있습니다. 처리량을 최대화하기 위해 워커당 HTTP 연결 풀 사용.
- **인앱 알림 저장**: 받은 편지함 기능을 위해 Cassandra(`(userId, timestamp)` 파티션)에 저장. 읽지 않은 수는 Redis 카운터로 관리.
- **전달 분석**: 열람률, 클릭률, 구독 취소 추적 — 속도 제한 조정과 전달성 문제 감지에 필수적입니다.
