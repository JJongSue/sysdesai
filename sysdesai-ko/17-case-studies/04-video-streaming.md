# 비디오 스트리밍 플랫폼 설계 (Netflix/YouTube)

> Source: https://www.sysdesai.com/learn/case-studies/video-streaming

---

## 문제 정의

비디오 스트리밍 플랫폼은 사용자가 비디오 콘텐츠를 업로드하고, 탐색하고, 시청할 수 있게 합니다. 두 가지 핵심 과제는: (1) **인제스천(Ingestion)** — 원본 업로드(최대 4K/8K)를 여러 화질 단계로 빠르게 처리하는 것, (2) **전달(Delivery)** — 수억 명의 동시 시청자에게 수십억 개의 비디오 세그먼트를 버퍼링 최소화로 제공하는 것입니다.

## 요구 사항

| 기능 요구 사항 | 비기능 요구 사항 |
| --- | --- |
| 최대 10 GB 비디오 업로드 | 2초 이내 재생 시작 |
| 다양한 화질로 스트리밍 (360p~4K) | 99.99% 스트리밍 가용성 |
| 대역폭 기반 적응형 비트레이트(ABR) | 하루 10억 이상 스트리밍 시작 지원 |
| 검색 및 추천 | 업로드 후 30분 이내 비디오 처리 완료 |
| 재생 이어보기, 챕터, 자막 | CDN을 통한 전 세계 낮은 지연 |

## 용량 추정

| 지표 | 추정치 |
| --- | --- |
| 분당 업로드 비디오 | 500시간 분량 (YouTube 규모) |
| 평균 원본 비디오 크기 | 1080p 기준 10분당 1 GB |

| 원본 비디오당 저장 용량 (10분) | ~1 GB 원본 + ~3 GB 트랜스코딩 |
| 일일 스트리밍 시작 수 | 10억 (세션당 평균 20분 = ~1 Pbps 대역폭) |
| CDN 이그레스 (평균 5 Mbps 비트레이트) | 피크 ~833 Tbps |

## 트랜스코딩과 적응형 비트레이트(ABR)

원본 비디오는 **HLS(HTTP Live Streaming)** 또는 **DASH(Dynamic Adaptive Streaming over HTTP)**를 사용하여 여러 렌디션으로 트랜스코딩됩니다. 각 렌디션은 2~10초 단위 청크로 분할됩니다. 플레이어는 현재 네트워크 상태에 따라 어떤 화질 세그먼트를 요청할지 선택하며, 중단 없이 중간에 전환할 수 있습니다.

| 화질 | 해상도 | 비트레이트 | 세그먼트 크기 (4초) |
| --- | --- | --- | --- |
| 360p | 640×360 | 400 Kbps | 200 KB |
| 480p | 854×480 | 800 Kbps | 400 KB |
| 720p | 1280×720 | 2.5 Mbps | 1.25 MB |
| 1080p | 1920×1080 | 5 Mbps | 2.5 MB |
| 4K | 3840×2160 | 15 Mbps | 7.5 MB |

> ℹ️
> 병렬 트랜스코딩
> 원본 비디오를 1분 단위 청크로 분할하고 GPU 팜에서 각 청크를 병렬로 트랜스코딩합니다. 2시간 영화는 120개의 독립적인 1분짜리 작업이 됩니다. 이를 통해 이용 가능 시간이 몇 시간에서 몇 분으로 단축됩니다. 완성된 세그먼트를 다시 마스터 플레이리스트로 합칩니다.

## CDN 전략

비디오 세그먼트는 변경되지 않는 파일이므로 — 적극적인 CDN 캐싱에 완벽합니다. Netflix의 **Open Connect**는 ISP 네트워크 내에 직접 맞춤형 CDN 어플라이언스를 배포하여 시청자와 같은 건물에 있을 수도 있는 서버에서 비디오를 제공합니다. 핵심 CDN 전략:

- **긴 캐시 TTL**: 비디오 세그먼트는 절대 변하지 않음 — 영구 캐시 (`Cache-Control: max-age=31536000, immutable`).
- **매니페스트 짧은 TTL**: `.m3u8` 플레이리스트는 라이브 스트림에서 업데이트될 수 있음 — 짧은 TTL (5~30초).
- **인기 콘텐츠 프리페칭**: 수요가 발생하기 전에 트렌딩 콘텐츠를 예측하고 CDN PoP를 사전 워밍.
- **지오 라우팅**: IP 지오로케이션과 BGP 애니캐스트를 기반으로 시청자를 가장 가까운 CDN PoP로 라우팅.

## 메타데이터 서비스

비디오 메타데이터(제목, 설명, 태그, 썸네일, 좋아요 수)는 구조화된 쿼리를 위해 MySQL에 저장되고 전문 검색을 위해 Elasticsearch에 인덱싱됩니다. 추천 엔진은 Kafka 이벤트(시청, 좋아요, 완료)로 구성된 데이터 웨어하우스에서 읽어 사용자별 추천 `videoId` 목록을 Redis에 씁니다.

## 확장성 고려 사항

- **트랜스코딩 팜 오토스케일링**: 작업 큐(SQS) + 자동 스케일링하는 스팟 GPU 인스턴스 사용. 우선순위 큐는 오래된 콘텐츠 재인코딩보다 새 업로드를 먼저 처리합니다.
- **재개 가능한 업로드**: 대용량 파일은 클라이언트 측 청크 재시도를 사용하는 S3 멀티파트 업로드 활용. 업로드 상태를 Redis에 저장하여 연결이 끊겨도 이어서 업로드 가능.
- **DRM(Digital Rights Management)**: AES-128 또는 Widevine/FairPlay로 세그먼트 암호화. 암호화 키는 CDN과 분리된 KMS(Key Management Service)에 저장.
- **분석 파이프라인**: 시청 이벤트(시작, 일시 정지, 탐색, 종료)를 Kafka → 데이터 웨어하우스로 스트리밍하여 콘텐츠 분석 및 ML 학습에 활용.
- **콜드 스토리지**: 월 1회 미만 재생되는 비디오는 Glacier 또는 동등한 콜드 스토리지로 이동하여 비용 절감.
