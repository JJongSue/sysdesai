# 라이드 셰어링 시스템 설계 (Uber)

> Source: https://www.sysdesai.com/learn/case-studies/ride-sharing

---

## 문제 정의

라이드 셰어링 플랫폼은 실시간으로 탑승자와 근처 드라이버를 연결합니다. 시스템은 수백만 대의 이동하는 드라이버 위치를 추적하고, 몇 초 안에 승차 요청을 가장 가까운 사용 가능한 드라이버와 매칭하며, ETA를 계산하고, 결제를 처리해야 합니다. 이 모든 것을 전 세계적으로 처리해야 합니다. 고유한 과제는 대규모의 **지리공간 실시간 매칭 문제**입니다.

## 요구 사항

| 기능 요구 사항 | 비기능 요구 사항 |
| --- | --- |
| 탑승자가 픽업/하차 위치로 탑승 요청 | 5초 이내 드라이버 매칭 |
| 드라이버가 4초마다 위치 전송 | 동시 드라이버 100만 명 지원 |
| 시스템이 탑승자를 가장 가까운 드라이버에 매칭 | 99.99% 가용성 |
| 탑승자 지도에 실시간 드라이버 위치 표시 | 위치 업데이트 지연 < 1초 |
| 공급/수요 비율에 따른 서지 프라이싱 | 시간당 승차 요청 100만 건 처리 |
| 이동 종료 시 결제 처리 | 전 세계 분산 (멀티 리전) |

라이드 셰어링 시스템 고수준 아키텍처

## 지리공간 인덱싱(Geospatial Indexing)

핵심 데이터 구조 과제는: **탑승자 위치가 주어졌을 때, 100ms 이내에 R km 이내의 K명의 가장 가까운 사용 가능한 드라이버를 찾는 것**입니다. 두 가지 일반적인 접근법:

| 접근법 | 동작 방식 | 장점 | 단점 |
| --- | --- | --- | --- |
| Redis GEO | 지오해시 인코딩된 정렬 셋 사용; GEORADIUS 명령 | 간단하고 내장되어 있으며 빠름 | 단일 노드 제한; 커스텀 필터링 불가 |
| Google S2 Geometry | 구의 계층적 셀 분해 | 유연하고 계층적이며 복잡한 쿼리 지원 | 커스텀 인덱싱 레이어 필요 |
| H3 (Uber 라이브러리) | 육각형 계층적 그리드 | 균일한 면적 셀, 밀도 분석에 탁월 | 덜 일반적; 운영 복잡성 증가 |

Uber는 내부적으로 **S2 셀**을 사용합니다. 면접에서는 Redis `GEORADIUS`로 충분히 설명 가능합니다: 드라이버는 `GEOADD drivers lon lat driverId`로 저장되고 `GEORADIUSBYMEMBER riders riderId 5 km ASC COUNT 10`으로 조회됩니다. 각 Redis GEO 작업은 O(N+log M)으로 실행됩니다 (N은 결과 수, M은 전체 항목 수).

## 드라이버 매칭 흐름

요청에서 드라이버 수락까지의 라이드 매칭 흐름

## 서지 프라이싱(Surge Pricing)

서지 프라이싱은 특정 지역에서 수요가 공급을 초과할 때 요금을 인상합니다. 시스템은 지역 셀(예: S2 레벨-12 셀 ≈ 3.7 km²)별로 **서지 배수**를 계산합니다. 해당 셀의 활성 승차 요청과 사용 가능한 드라이버를 비교하는 방식입니다. Kafka는 승차 요청과 드라이버 가용성 이벤트를 스트리밍하고, Flink 작업이 30초마다 셀별 비율을 집계하여 서지 팩터를 Redis에 씁니다. 라이드 서비스는 요청 시점에 서지 팩터를 읽습니다.

## 위치 업데이트 파이프라인

드라이버는 WebSocket을 통해 4초마다 위치를 전송합니다. 드라이버 100만 명 기준, 지오 인덱스에 **25만 쓰기/초**가 발생합니다. Redis는 이 규모를 처리할 수 있지만(단일 노드에서 초당 100만+ 작업 처리 가능), 이중화를 위해 Redis 클러스터가 필요합니다. 이동 재현 및 분석을 위한 위치 이력은 비동기로 Cassandra에 영구 저장됩니다 (시계열: `(tripId, timestamp) → lat, lon`).

> ⚠️
> 위치 데이터 프라이버시
> 원본 드라이버 및 탑승자 위치 데이터는 민감합니다. 암호화하여 저장하고, 필요한 것만 보관하며(이동 시간 + 유예 기간), 접근 제어를 구현하세요. 면접에서 프라이버시와 데이터 보존에 대해 언급하면 엔지니어링 성숙도를 보여줍니다.

## 확장성 고려 사항

- **도시별 샤딩**: 모든 서비스와 데이터 저장소를 도시/지역별로 파티셔닝합니다. 뉴욕의 드라이버와 탑승자는 런던의 사람들과 상호작용하지 않습니다 — 이것이 자연스러운 샤딩 키입니다.
- **WebSocket 서버 풀**: driverId 기반 일관된 해싱으로 스티키 세션을 사용하여 위치 업데이트가 항상 같은 서버에 도달하도록 합니다. 해당 서버는 WebSocket을 유지하고 Redis를 업데이트합니다.
- **이동 DB**: ACID 보장을 위해 `tripId`로 샤딩된 MySQL 사용. 결제 및 이동 상태 전환에 적합.
- **ETA 서비스**: Google Maps API와 통합하거나 내부 라우팅 엔진(OSRM) 유지. (출발_셀, 도착_셀) 쌍별 ETA 계산을 5분 TTL로 Redis에 캐시.
- **멀티 리전**: 대륙별로 배포하고 글로벌 로드 밸런싱 사용. 라이드 생성은 로컬이며, 결제 시스템은 최종 일관성을 가진 전역 시스템입니다.

> 💡
> 인터뷰 팁
> 지리공간 인덱싱 질문이 좋은 답변과 훌륭한 답변을 가릅니다. Redis GEOADD/GEORADIUS가 정렬 셋의 지오해시로 구현된다는 것을 알고 있어야 합니다. 드라이버 수락에 15초 타임아웃이 있고, 초과 시 다음 후보로 폴백한다는 점을 언급하세요 — 이는 매칭의 UX와 장애 모드를 충분히 생각해 봤음을 보여줍니다.
