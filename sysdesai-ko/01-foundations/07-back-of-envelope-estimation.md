# 대략적인 추정 (Back-of-the-Envelope Estimation)

> 출처: https://www.sysdesai.com/learn/foundations/back-of-envelope-estimation

---

## 추정이 중요한 이유

**대략적인 추정(Back-of-the-envelope estimation)**은 설계 결정을 내리기 위해 규모(Order-of-magnitude)를 대략적으로 계산해보는 연습입니다. 이는 다음과 같은 질문에 답을 줍니다: "샤딩(Sharding)이 필요할까?", "단일 캐시 노드(Cache Node)로 충분할까?", "이 기능에 대역폭(Bandwidth)은 얼마나 필요할까?". 추정 없는 설계는 추측일 뿐이지만, 추정이 동반된 설계는 근거 있는 엔지니어링 선택이 됩니다.

인터뷰에서 추정은 두 가지 목적을 수행합니다: 정량적인 사고방식을 보여주고, 설계가 감당해야 할 규모(Scale)를 명확히 합니다. 그리고 이는 이후의 모든 아키텍처 선택의 근거가 됩니다.

> 💡
> 인터뷰 팁
> 면접관이 요청하지 않더라도 항상 명시적으로 추정을 수행하세요. 요구사항을 명확히 한 후에 "설계를 시작하기 전에 규모를 먼저 추정해보겠습니다"라고 말하세요. 그 다음 QPS, 저장 용량, 대역폭을 도출하세요. 이는 당신이 정량적으로 사고하는 엔지니어임을 보여주며, 실제로 캐시 계층, 샤딩, CDN 등이 필요한지 판단할 근거가 됩니다.

## 필수 참고 수치

다음 수치들은 반드시 기억해 두세요. 모든 추정의 기초 자료가 됩니다. 구글의 제프 딘(Jeff Dean)이 발표한 '모든 엔지니어가 알아야 할 수치들'은 업계의 표준 참고 자료가 되었습니다.

| 작업 | 지연 시간(Latency) | 비고 |
| --- | --- | --- |
| L1 캐시 히트(L1 cache hit) | ~1 ns | 가장 빠름; CPU 캐시에 데이터가 있음 |
| L2 캐시 히트(L2 cache hit) | ~10 ns | 칩 내부에 있지만 L1보다는 느림 |
| 메인 메모리(RAM) 접근 | ~100 ns | L1보다 100배 느림 |
| SSD 랜덤 읽기 (NVMe) | ~100 µs | RAM보다 약 1,000배 느림 |
| HDD 랜덤 읽기 (Seek) | ~10 ms | 기계식 디스크: 랜덤 I/O는 피해야 함 |
| 동일 데이터 센터 내 네트워크 | ~500 µs | DC 내부; 예측 가능함 |
| 네트워크 왕복 (대륙 간) | ~150 ms | 빛의 속도 + 라우팅(Routing) 지연 |
| 네트워크 왕복 (전 세계) | ~300 ms | 최악의 경우; CDN 도입의 근거가 됨 |

| 단위 | 값 | 비고 |
| --- | --- | --- |
| 1 KB | 1,000 바이트 | 트윗 하나, 짧은 이메일 |
| 1 MB | 1,000,000 바이트 | 압축된 사진, 1분의 오디오 |
| 1 GB | 1,000,000,000 바이트 | 압축된 영화 한 편, 사진 1,000장 |
| 1 TB | 1,000 GB | 하드 드라이브 하나, 사진 약 100만 장 |
| 1 PB | 1,000 TB | 대규모 데이터 웨어하우스, CDN 캐시 |
| 하루의 초 수 | 86,400초 | 빠른 계산을 위해 100,000초 사용 가능 (약 15% 오차) |
| 1년의 초 수 | 약 3,150만 초 | 빠른 계산을 위해 3,000만 초 사용 가능 |

## 트래픽을 QPS로 변환하기

초당 요청 수(QPS 또는 RPS)는 가장 기본적인 메트릭(Metric)입니다. 대부분의 요구사항은 일일 활성 사용자 수(DAU) 또는 월간 활성 사용자 수(MAU)로 주어집니다. 이를 변환하는 방법은 다음과 같습니다.

```
# QPS 추정 공식:
# 평균 QPS = 하루 총 요청 수 / 86,400초

# 유용한 단축 계산:
# 하루 100만(1M) 요청    ≈ 12 QPS
# 하루 1,000만(10M) 요청  ≈ 116 QPS
# 하루 1억(100M) 요청     ≈ 1,160 QPS
# 하루 10억(1B) 요청      ≈ 11,600 QPS

# 최대(Peak) QPS 계산 원칙:
# 최대 트래픽은 보통 평균의 2~3배임 (트래픽은 균일하지 않음)
# 최대 QPS ≈ 평균 QPS × 3

# 예시: DAU 3억 명인 트위터, 사용자당 분당 5개의 트윗 조회
# 분당 읽기 수 = 3억 × 5 = 15억 회/분
# 초당 읽기 수 (평균) = 15억 / 60 = 2,500만 QPS
# 최대 QPS ≈ 2,500만 × 3 = 7,500만 QPS (새해 첫날 같은 주요 이벤트 시)
```

## 저장 용량 추정 (Storage Estimation)

저장 용량은 시간이 지남에 따라 늘어납니다. 항상 하루에 생성되는 새로운 데이터의 양을 추정한 뒤, 보관 기간(Retention Horizon)을 곱하여 총 필요 용량을 구하세요.

```
# 저장 용량 추정 공식:
# 일일 저장 용량 = (일일 쓰기 횟수) × (평균 객체 크기)
# 총 저장 용량 = 일일 저장 용량 × 보관 기간(일)
# 여기에 복제 계수(Replication Factor)를 추가 (분산 시스템은 보통 3배)

# 예시: URL 단축 서비스
# - 하루에 1억(100M) 개의 새로운 URL 생성
# - 각 URL 레코드: 단축 코드(7바이트) + 원본 URL(평균 100바이트) + 메타데이터(50바이트) = 약 200바이트
# - 일일 저장 용량 = 1억 × 200바이트 = 20 GB/일
# - 5년 보관 시 = 20 GB × 365 × 5 = 36.5 TB (원본 데이터)
# - 3배 복제 시 = 36.5 TB × 3 = 약 110 TB (전체 용량)

# 예시: 이미지 호스팅 (인스타그램 규모)
# - 하루에 1억(100M) 개의 새로운 사진 업로드
# - 사진 평균: 원본 3MB, 썸네일(Thumbnail) 500KB, 마이크로 썸네일 100KB
# - 사진당 저장 용량: 총 3.6 MB
# - 일일 저장 용량: 1억 × 3.6 MB = 360 TB/일
# - 연간 용량: 360 TB × 365 = 약 131 PB/년 (→ CDN 및 객체 스토리지(Object Storage) 필수)
```

## 대역폭 추정 (Bandwidth Estimation)

대역폭은 초당 저장되는 데이터의 양과 같습니다. 높은 대역폭 요구사항은 CDN 사용, 콘텐츠 압축, 청크 단위 스트리밍 아키텍처 도입의 근거가 됩니다.

```
# 대역폭 추정 공식:
# 유입(Inbound) 대역폭 = 쓰기 QPS × 평균 객체 크기
# 유출(Outbound) 대역폭 = 읽기 QPS × 평균 객체 크기

# 예시: 비디오 스트리밍 (넷플릭스 규모)
# - 저녁 피크 시간대 동시 시청자 2억 명
# - 평균 비디오 비트레이트(Bitrate): 5 Mbps (HD 화질)
# - 총 유출 대역폭 = 2억 × 5 Mbps = 1,000,000,000 Mbps = 1 Exabit/초
# → 이것이 넷플릭스가 ISP 내부에 서버를 두는 CDN(Open Connect)을 사용하는 이유입니다.
#   중앙 데이터 센터에서 1 Ebit/s를 서비스하는 것은 불가능에 가깝습니다.

# 유용한 대역폭 기준점:
# 표준 1G NIC: 1 Gbps = 125 MB/s
# 단일 10G NIC: 10 Gbps = 1.25 GB/s
# 계산된 대역폭이 100 Gbps를 넘으면 CDN이 필요하다고 판단하세요.
```

## 체계적인 추정 템플릿

모든 추정 시 이 템플릿을 활용하세요. 체계적으로 따라가면 2~3분 안에 모든 설계 결정의 근거가 되는 수치들을 얻을 수 있습니다.

1. **가정 설정** — DAU, 사용자당 일일 요청 수, 읽기/쓰기 비율, 평균 객체 크기 등을 정합니다.
2. **쓰기 QPS 계산** — 초당 생성되는 새로운 데이터 양을 구합니다.
3. **읽기 QPS 계산** — 초당 읽히는 데이터 양을 구합니다 (보통 쓰기의 10~100배).
4. **일일 저장 용량 증가량 계산** — 쓰기 QPS × 하루 초 수 × 객체 크기.
5. **총 저장 용량 계산** — 일일 증가량 × 보관 기간 × 복제 계수.
6. **대역폭 계산** — 유출은 읽기 QPS × 객체 크기, 유입은 쓰기 QPS × 객체 크기.
7. **결론 도출** — CDN이 필요한가? 샤딩이 필요한가? 특수한 저장 계층(Storage Tier)이 필요한가?

📌
전체 추정 예시: Pastebin

가정: DAU 1,000만 명, 사용자당 주당 평균 1개의 텍스트 생성, 하루에 텍스트당 10회 읽기 발생, 텍스트 평균 크기 10 KB.
쓰기 QPS = (1,000만 × 1/7) / 86,400 ≈ 17 QPS.
읽기 QPS = 1,000만 × 10 / 86,400 ≈ 1,160 QPS.
읽기/쓰기 비율 ≈ 68:1 (읽기 비중이 매우 높음).
일일 저장 용량 = 17 × 86,400 × 10 KB ≈ 14.7 GB/일.
10년치 저장 용량 = 14.7 × 365 × 10 ≈ 53.7 TB.
3배 복제 시: 약 160 TB.
결론: 단일 데이터베이스로 쓰기 QPS 처리가 가능함; 읽기 트래픽이 많으므로 캐시 계층이 효과적임; 텍스트 내용 저장을 위해 객체 스토리지(Object Storage) 사용; 이 규모에서는 CDN이 필수적이지 않음.

## 흔히 저지르는 추정 실수들

- **읽기/쓰기 비율 무시** — 대부분의 시스템은 읽기 비중이 100:1 이상으로 압도적입니다. 항상 "읽기/쓰기 비율이 어떻게 되나요?"라고 물으세요. 이는 캐싱과 쓰기 최적화 저장소 중 무엇이 우선순위인지 결정합니다.
- **복제(Replication) 누락** — 3배 복제는 저장 비용을 세 배로 늘립니다. 항상 원본 용량에 복제 계수를 곱하세요.
- **평균값과 최대값 혼동** — 시스템은 평균이 아닌 최대 트래픽(평균의 3배)을 기준으로 설계해야 합니다. 평소에는 괜찮다가 새해 전날에 뻗어버리는 시스템은 잘못 설계된 시스템입니다.
- **과도한 정밀도** — "약 600 QPS" 대신 "578.7 QPS"라고 계산하는 것은 시간 낭비이며 잘못된 정밀함을 암시합니다. 과감하게 반올림하고 다음 단계로 넘어가세요.
- **메타데이터(Metadata) 무시** — 저장되는 객체에는 생성 시간, 소유자, 태그, 권한 등 무시할 수 없는 크기의 메타데이터가 붙습니다. 이를 계산에 포함하는 것을 잊지 마세요.

> 인터뷰 팁
> 머릿속으로만 계산하지 말고 인터뷰 화면이나 화이트보드에 구조적으로 적으세요. 공식을 적고 수치를 대입한 뒤 결론을 말하세요: "쓰기는 17 QPS이므로 단일 DB로 충분합니다. 읽기는 1,160 QPS이므로 캐시가 필요하겠네요." 이렇게 기록하면 당신과 면접관 모두의 참고 자료가 되며, 계산 도중 길을 잃는 것을 방지해줍니다. 빠른 곱셈을 위해 하루를 100,000초로 계산하는 등 둥근 숫자를 사용하세요.
