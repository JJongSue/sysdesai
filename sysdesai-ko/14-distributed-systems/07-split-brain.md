# Split-Brain 문제

> Source: https://www.sysdesai.com/learn/distributed-systems/split-brain

## Split-Brain이란?

**Split-Brain**은 네트워크 파티션(Network Partition)이 클러스터를 둘 이상의 그룹으로 분리하고, 각 그룹이 자신이 과반수라고 독립적으로 판단하여 자체 리더를 선출할 때 발생합니다. 두 리더 모두 쓰기를 수락하고, 파티션이 회복되면 두 파티션이 서로 다른 상태로 발산되어 자동 조정이 불가능할 수 있습니다. 이는 분산 데이터베이스에서 가장 위험한 장애 유형 중 하나입니다.

Split-Brain: 두 파티션 모두 리더를 선출하고 서로 다른 쓰기를 수락

예시: 5-노드 데이터베이스 클러스터가 3개 그룹과 2개 그룹으로 분리됩니다. 2개 그룹은 네트워크 파티션을 알지 못한 채 새 리더를 선출하고 쓰기를 수락하기 시작합니다. 원래의 3개 그룹도 쓰기를 수락하는 리더를 유지합니다. 파티션이 회복되면 두 그룹 모두 동일한 데이터에 상충되는 변경을 가한 상태가 됩니다.

## 예방: 쿼럼 기반 합의(Quorum-Based Consensus)

Split-Brain에 대한 주요 방어 수단은 **쿼럼 기반 합의**입니다. 리더는 클러스터 과반수(N/2 + 1) 노드의 승인이 있을 때만 선출되고 쓰기를 커밋할 수 있습니다. 클러스터에서 두 개의 과반수가 동시에 존재할 수 없으므로 Split-Brain이 불가능합니다.

- 5-노드 클러스터에서 과반수 = 3. 2개 파티션은 리더를 선출하거나 쓰기를 커밋할 수 없습니다.
- 3-노드 클러스터에서 과반수 = 2. 1개 파티션은 리드할 수 없지만, 2개 파티션은 여전히 리더를 선출할 수 있습니다.
- 따라서 홀수 클러스터 크기가 강력히 권장되는 이유입니다 — 짝수 클러스터는 추가 장애 허용성 없이 한 표를 낭비합니다(4-노드 ≈ 실질적으로 3-노드).

| 클러스터 크기 | 필요 과반수 | 장애 허용 노드 수 | 비고 |
| --- | --- | --- | --- |
| 3 | 2 | 1 | 장애 허용의 최소 단위 |
| 5 | 3 | 2 | 일반적인 프로덕션 선택 |
| 7 | 4 | 3 | 대규모 고가용성 클러스터 |
| 4 | 3 | 1 | 3-노드 클러스터와 다를 바 없음 |
| 6 | 4 | 2 | 5-노드 클러스터와 다를 바 없음 |

## 펜싱 토큰(Fencing Token)

쿼럼이 있더라도 **프로세스 일시 정지**로 인한 미묘한 Split-Brain이 발생할 수 있습니다. 새 텀으로 새 리더가 선출되었지만, 오래된 리더(GC나 OS 스케줄링으로 일시 정지됨)가 재개되어 자신이 여전히 리더라고 생각하는 경우입니다. 네트워크 연결이 없어 확인도 할 수 없습니다. 이는 **펜싱 토큰** — 각 리더십 부여 시 발급되는 단조 증가(Monotonically Increasing) 숫자 — 으로 완화됩니다.

리더가 하는 모든 쓰기에는 펜싱 토큰이 포함되어야 합니다. 스토리지 시스템은 지금까지 본 가장 높은 토큰보다 낮은 펜싱 토큰의 쓰기를 거부합니다. 오래된 리더가 재개되어 이전(낮은) 토큰으로 쓰기를 시도하면 스토리지가 거부하여 — 오래된 리더가 데이터를 손상시키는 것을 방지합니다.

```pseudocode
// 펜싱 토큰 적용 스토리지 시스템
class FencedStorage:
  highestSeenToken = 0

  function write(key, value, fencingToken):
    if fencingToken < highestSeenToken:
      return ERROR_STALE_LEADER  // 오래된 리더의 쓰기 거부
    highestSeenToken = fencingToken
    data[key] = value
    return SUCCESS

// 리더는 선출 시 토큰을 획득 (예: ZooKeeper에서)
// leaderToken = zookeeper.getEphemeralNode().sessionId (단조 증가)
// 모든 쓰기에 leaderToken 포함
```

## STONITH: 다른 노드를 강제 종료하기

**STONITH**(Shoot The Other Node In The Head)는 고가용성 클러스터링에서 사용되는 하드웨어 수준 펜싱 전략입니다. 노드가 불량 리더로 의심될 때, 클러스터는 대역외(Out-of-Band) 관리 인터페이스(IPMI, iDRAC, AWS EC2 종료 API)를 통해 강제로 전원을 끕니다. 파티션으로 분리되어 살아 있는 노드는 전원 종료 명령으로부터 스스로를 방어할 수 없으므로, 소프트웨어 수준 펜싱보다 더 신뢰할 수 있습니다.

> 📌
> 실제 사례: MongoDB 레플리카 셋의 Split-Brain
> MongoDB 레플리카 셋이 파티션됩니다. Primary(구)는 격리되고, Secondary + Arbiter가 3개 중 2개의 쿼럼을 형성하여 새 Primary를 선출합니다. 구 Primary에 대한 쓰기는 로컬에서 성공하지만 파티션이 회복되면 롤백됩니다. MongoDB는 **oplog 롤백** 메커니즘으로 이를 처리하지만, 파티션 동안 구 Primary에 쓰인 데이터는 손실됩니다. 따라서 내구성 보장을 위해 `writeConcern: majority`가 매우 중요합니다.

> 💡
> 인터뷰 팁
> 면접에서 복제나 데이터베이스 클러스터를 논의할 때 Split-Brain을 먼저 언급하세요. 쿼럼(과반수)을 예방 메커니즘으로, 펜싱 토큰을 오래된 리더에 대한 최후 방어책으로 설명하고, 홀수 클러스터 크기는 임의적인 게 아니라 노드당 장애 허용성을 최대화한다는 점을 언급하세요. MongoDB에 대해 질문받으면 `writeConcern: majority`가 Primary 장애 시에도 쓰기 내구성을 보장하는 안전장치라고 설명하세요.
