# Object Storage (S3 Pattern) (객체 스토리지, S3 패턴)

> Source: https://www.sysdesai.com/learn/data-storage/object-storage

---

## Three Storage Paradigms (세 가지 스토리지 패러다임)

객체 스토리지를 깊이 있게 다루기 전에, 시스템 엔지니어가 다루는 다른 두 가지 스토리지 패러다임과 어떻게 다른지 이해하는 것이 중요합니다.

| Paradigm(패러다임) | Access Model(액세스 모델) | Examples(예시) | Best For(용도) |
| --- | --- | --- | --- |
| Block Storage(블록 스토리지) | 디스크 인터페이스를 통한 고정 크기 블록 (하드 드라이브와 유사) | AWS EBS, GCP Persistent Disk | OS 파일 시스템, 데이터베이스, VM — 랜덤 읽기/쓰기 액세스가 필요한 모든 것 |
| File Storage(파일 스토리지, NAS) | 디렉토리 트리 구조의 계층적 파일 시스템 | AWS EFS, NFS, Samba | 여러 서버가 동시에 접근하는 공유 파일 시스템 |
| Object Storage(객체 스토리지) | HTTP API (GET/PUT/DELETE)를 통한 평면적 네임스페이스 | AWS S3, GCS, Azure Blob | 이미지, 비디오, 백업, 로그, ML 데이터셋 등 대규모 비구조화 데이터 |

## How Object Storage Works (객체 스토리지의 작동 원리)

객체 스토리지는 디렉토리 계층 구조가 없습니다 — 각 객체가 **Bucket Name(버킷 이름) + Object Key(객체 키)** (예: `photos/user-42/avatar.jpg`와 같이 경로처럼 보일 수 있는 문자열)로 식별되는 **Flat Namespace(평면적 네임스페이스)**입니다. 객체는 한 번 쓰여지면 변경할 수 없는 Immutable(불변) 상태입니다 — 파일을 업데이트하려면 전체 객체를 덮어써야 합니다. 이러한 불변성은 S3가 자랑하는 극도의 내구성과 확장성을 가능하게 합니다.

AWS S3는 각 객체를 여러 가용 영역(Availability Zone)에 걸쳐 저장함으로써 **11 nines of durability(99.999999999%의 내구성)**를 제공합니다. 객체가 스토리지 노드의 정족수(Quorum)에 기록되면 내구성이 확보된 것으로 간주됩니다. S3 Standard는 또한 **99.99%의 가용성(Availability)**을 제공합니다 — 이는 내구성과는 별개의 개념입니다. 내구성은 데이터가 존재함을 의미하고, 가용성은 해당 데이터에 접근할 수 있음을 의미합니다.

## Consistency Model (일관성 모델)

2020년 12월부터 Amazon S3는 모든 작업(GET, PUT, DELETE, LIST)에 대해 **Strong Read-after-write Consistency(강한 쓰기 후 읽기 일관성)**를 제공합니다. 이전에는 최종 일관성(Eventual Consistency)을 가졌기 때문에, 객체를 PUT하고 즉시 GET했을 때 가끔 404 에러를 받는 놀라운 버그가 발생하곤 했습니다. 업데이트된 모델 덕분에 성공적인 PUT 이후의 GET 요청은 즉시 최신 데이터를 볼 수 있게 되었으며, 이는 사용성을 크게 개선했습니다.

> ℹ️
> S3 최종 일관성의 역사 (S3 Eventual Consistency History)
> 오래된 시스템 디자인 자료에서 S3의 덮어쓰기 작업에 대한 최종 일관성을 경고하는 내용을 본다면, 이는 2020년에 해결되었음을 기억하세요. 현재 S3는 모든 작업에 대해 강한 일관성을 제공합니다. 이는 파일을 업로드하고 즉시 처리하는 패턴 — 추가적인 동기화 없이도 안전한 워크플로우를 가능하게 합니다.

## Key Features for System Design (시스템 디자인을 위한 핵심 기능)

### Versioning (버전 관리)

버킷에 버전 관리를 활성화하면 모든 객체의 모든 버전을 유지할 수 있습니다. 삭제 작업은 **Delete Marker(삭제 마커)**가 되어 객체가 물리적으로 제거되지 않습니다. 언제든 이전 버전으로 복구할 수 있습니다. 이는 백업 시스템, 소스 데이터를 재처리해야 하는 데이터 파이프라인, 그리고 규제 준수 요구 사항에 필수적입니다.

### Lifecycle Policies (수명 주기 정책)

**Lifecycle Policies(수명 주기 정책)**는 비용 최적화를 자동화합니다. 다음과 같은 규칙을 정의할 수 있습니다: 30일 후 객체를 **S3 Infrequent Access**로 전환(저장 비용은 저렴하지만 조회 비용은 높음), 90일 후 **S3 Glacier**로 전환(매우 저렴하지만 조회에 몇 분에서 몇 시간 소요), 365일 후 객체 만료(삭제). 이를 통해 수동 개입 없이 데이터를 자동으로 계층화합니다.

```json
{
  "Rules": [
    {
      "ID": "log-lifecycle",
      "Status": "Enabled",
      "Transitions": [
        { "Days": 30, "StorageClass": "STANDARD_IA" },
        { "Days": 90, "StorageClass": "GLACIER" }
      ],
      "Expiration": { "Days": 365 }
    }
  ]
}
```

### Pre-Signed URLs (사전 서명된 URL)

**Pre-signed URL(사전 서명된 URL)**은 수신자가 AWS 자격 증명을 가질 필요 없이 비공개 S3 객체에 일시적으로 접근할 수 있게 해줍니다. 서버는 자신의 자격 증명과 만료 시간(예: 15분)으로 서명된 URL을 생성합니다. 클라이언트는 이 URL을 사용하여 S3에 직접 업로드하거나 다운로드합니다. 이는 사용자 파일 업로드를 위한 표준 패턴입니다 — 클라이언트가 서버를 거치지 않으므로 서버 부하와 비용을 줄일 수 있습니다.

## Object Storage Anti-Patterns (객체 스토리지 안티 패턴)

- **S3를 데이터베이스로 사용**: S3는 쿼리 기능이 없습니다. 모든 객체를 나열(list)하지 않고는 메타데이터로 객체를 필터링할 수 없습니다. 메타데이터와 객체 키를 저장하려면 데이터베이스(DynamoDB)를 사용하고, 실제 데이터(Blob) 저장에만 S3를 사용하세요.
- **핫 키 접두사 (Hot Key Prefix)**: S3는 키 접두사를 기준으로 파티셔닝합니다. 모든 객체가 동일한 접두사(예: 날짜 `2024-01-15/`)로 시작하면 동일한 파티션에 몰리게 됩니다. 고처리량 워크로드의 경우 접두사를 무작위로 하거나 해싱하여 여러 파티션에 분산시키세요.
- **작은 파일 저장**: S3는 요청당 비용이 발생합니다. 수백만 개의 아주 작은 파일(< 1KB)은 소수의 큰 파일보다 운영 비용이 훨씬 많이 듭니다. 저장하기 전에 작은 파일들을 배치(batch)로 묶으세요.

> 💡
> Interview Tip (인터뷰 팁)
> 객체 스토리지는 거의 모든 대규모 시스템 디자인에 등장합니다. "사용자가 사진을 업로드한다"거나 "비디오 파일을 저장한다"고 말할 때, 즉시 Pre-signed URL 패턴을 덧붙이세요: "클라이언트는 API 서버에서 사전 서명된 URL을 요청한 다음 S3에 직접 업로드합니다. 이를 통해 대용량 바이너리 전송이 애플리케이션 서버를 거치지 않게 하여 대역폭 비용을 획기적으로 줄일 수 있습니다." 추가 점수: 읽기가 많은 콘텐츠(사용자 아바타, 썸네일)를 위해 S3 앞에 CDN을 언급하세요.
