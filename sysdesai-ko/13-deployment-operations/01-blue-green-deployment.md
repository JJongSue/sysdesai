# Blue-Green Deployment

> 원문: https://www.sysdesai.com/learn/deployment-operations/blue-green-deployment

---

## Blue-Green Deployment란 무엇인가?

**Blue-green deployment**는 Blue와 Green이라 불리는 **두 개의 동일한 운영 환경(production environments)**을 항상 유지하는 방식입니다. 특정 시점에는 하나의 환경만 가동(운영 트래픽 처리)되며, 다른 하나는 유휴 상태로 대기하다가 다음 배포에 사용됩니다. 새로운 버전을 유휴 환경에 배포하고 테스트를 거친 뒤, 라우터나 로드 밸런서 설정을 변경하여 100%의 트래픽을 새 환경으로 한꺼번에 즉시 전환합니다.

핵심은 트래픽 전환이 **즉각적이고 가역적(reversible)**이라는 점입니다. 새 버전에 치명적인 버그가 발견되면 몇 초 만에 라우터를 이전 환경으로 되돌릴 수 있습니다. 재배포나 롤백 스크립트 실행, 컨테이너가 뜰 때까지 기다릴 필요가 전혀 없습니다.

트래픽 전환 전: Blue가 운영 중이며, Green은 검증을 기다리는 새 버전을 보유하고 있습니다.

## 단계별 배포 흐름

1. **유휴 환경 식별.** Blue가 운영 중이라면 Green에 배포합니다.
2. **새 버전을 Green에 배포.** 새로운 컨테이너 이미지, 업데이트된 설정, (하위 호환이 가능한 경우) 마이그레이션을 포함한 전체 배포를 수행합니다.
3. **Green에 대해 smoke 테스트 및 헬스 체크(health checks) 수행.** Green은 트래픽을 받고 있지 않으므로 실제 운영 인프라와 데이터를 사용해 안전하게 테스트할 수 있습니다.
4. **라우터 전환.** 로드 밸런서, DNS 가중치 기반 라우팅, 또는 서비스 메시의 가상 서비스(virtual service) 설정을 업데이트하여 트래픽의 100%를 Green으로 유도합니다.
5. **새 환경을 면밀히 모니터링.** 전환 후 첫 15~30분 동안 집중적으로 관찰합니다.
6. **Blue를 활성 상태로 유지.** Blue를 즉시 해제(decommission)하지 마세요. 즉각적인 롤백 대상으로서 유지해야 합니다.
7. **안정성이 확인되면**, Blue는 다음 주기를 위한 새로운 유휴 환경이 됩니다.

## 트래픽 전환 매커니즘

| 매커니즘 | 작동 방식 | 전환 속도 | 롤백 속도 |
| --- | --- | --- | --- |
| DNS TTL flip | DNS A 레코드를 Green의 IP로 업데이트 | 수 분 (TTL에 따라 다름) | 수 분 |
| 로드 밸런서 타겟 교체 | ALB/NLB의 타겟 그룹 변경 | 수 초 | 수 초 |
| 서비스 메시 가상 서비스 | Istio VirtualService 가중치 업데이트 | 1초 미만 | 1초 미만 |
| Feature flag / 라우팅 헤더 | 헤더나 플래그에 따라 라우팅 | 즉시 | 즉시 |

> ⚠️
> DNS TTL의 함정
> DNS를 통한 전환은 가장 느리고 까다로운 옵션입니다. DNS 레코드는 TTL 값에 따라 ISP와 클라이언트에 의해 캐싱됩니다. TTL을 60초로 설정하더라도 일부 리졸버(resolvers)는 낮은 TTL을 무시하기도 합니다. 진정한 제로 다운타임 전환(zero-downtime cutover)을 원한다면 DNS가 아닌 로드 밸런서 타겟 그룹 교체나 서비스 메시를 사용하세요.

## 데이터베이스 마이그레이션: 가장 어려운 부분

Blue-green deployment는 상태가 없는(stateless) 애플리케이션 계층에서는 훌륭하게 작동합니다. 하지만 어려운 부분은 **데이터베이스 스키마 변경(database schema changes)**입니다. 두 환경은 일반적으로 하나의 데이터베이스(또는 복제된 클러스터)를 공유합니다. 만약 v2.0에서 v1.0과 호환되지 않는 스키마 변경(예: v1.0이 여전히 읽고 있는 컬럼 삭제)이 필요하다면, 이전 환경을 깨뜨리지 않고는 트래픽을 되돌릴 수 없습니다.

해결책은 **expand-contract 패턴**(병렬 변경 또는 다단계 마이그레이션이라고도 함)을 사용하는 것입니다:

1. **Expand (확장):** 새로운 컬럼이나 테이블만 *추가*하는 마이그레이션과 함께 v2.0을 배포합니다. v1.0은 여전히 잘 작동하며 새로운 컬럼은 무시합니다.
2. **데이터 마이그레이션:** 두 환경이 모두 실행되는 동안 데이터를 새 스키마로 채웁니다(backfill).
3. **Cut over (전환):** 트래픽을 v2.0으로 전환합니다.
4. **Contract (수축):** v2.0의 안정성이 완전히 확인되고 v1.0이 해제된 후, 이전 컬럼이나 테이블을 삭제하는 두 번째 마이그레이션을 실행합니다.

> ℹ️
> 별도의 데이터베이스 환경
> 일부 팀은 환경별로 완전히 분리된 데이터베이스를 운영하기도 합니다. 이는 마이그레이션 충돌 문제를 해결하지만, 전환 전 데이터 동기화가 필요합니다. 이는 주로 배포 윈도우 동안 Blue의 데이터베이스에서 Green으로 CDC(change data capture) 복제를 통해 이루어집니다.

## 비용 및 트레이드오프

| 구분 | Blue-Green 장점 | Blue-Green 단점 |
| --- | --- | --- |
| 롤백 속도 | 즉시 가능 (수 초) | — |
| 다운타임 | 전환 중 제로 다운타임 | — |
| 인프라 비용 | — | 항상 두 배의 컴퓨팅 비용 발생 |
| 데이터베이스 마이그레이션 | — | expand-contract 원칙 준수 필요 |
| 상태 유지 세션(Stateful sessions) | — | 전환 시 진행 중인 세션이 끊길 수 있음 |
| 테스트 신뢰도 | 운영 환경과 동일한 인프라에서 테스트 가능 | — |

## AWS 구현 예시

yaml

```
# Blue-Green ECS 배포를 위한 AWS CodeDeploy appspec.yml
version: 0.0
Resources:
  - TargetService:
       Type: AWS::ECS::Service
       Properties:
         TaskDefinition: <TASK_DEFINITION>
         LoadBalancerInfo:
           ContainerName: "my-app"
           ContainerPort: 8080

# CodeDeploy는 대체 작업 세트(Green)를 생성하고,
# 헬스 체크 통과 시 트래픽을 전환한 뒤,
# 기존 작업 세트(Blue)를 종료합니다.
# 종료 지연 시간: 5분 (롤백 윈도우 확보).
Hooks:
  AfterAllowTestTraffic:
    - Location: scripts/run-smoke-tests.sh
      Timeout: 300
```

**Kubernetes**에서 blue-green은 서로 다른 레이블을 가진 두 개의 `Deployment` 객체를 유지함으로써 달성됩니다. `Service` 셀렉터를 업데이트하여 새로운 배포를 가리키게 합니다. **Argo Rollouts**나 **Flagger** 같은 도구는 전환 후 헬스 체크 실패 시 자동 롤백을 포함하여 이 패턴을 자동화해 줍니다.

## Blue-Green을 사용해야 하는 경우

- 즉각적인 롤백 능력이 필수적인 **고위험 릴리스**
- 제로 다운타임 유지보수 윈도우가 필요한 **규제 환경**
- 지속적 배포보다는 **드물게 발생하는 대규모 배치 릴리스** (주간 또는 월간)
- 데이터베이스 마이그레이션 전략 관리가 가능한 **stateless 서비스**

> 💡
> 인터뷰 팁
> 면접에서 blue-green deployment를 제안한다면, 즉시 데이터베이스 문제를 언급하세요. 면접관이 기대하는 후속 질문입니다. "까다로운 부분은 스키마 변경입니다. 저는 expand-contract 패턴을 사용하겠습니다. 먼저 하위 호환이 가능한 마이그레이션을 배포하고, 트래픽을 전환한 뒤, 이전 환경이 해제되면 정리 마이그레이션을 실행하는 방식입니다."라고 답하세요. 이는 단순한 패턴 명칭 이상의 깊은 이해도를 보여줍니다.
