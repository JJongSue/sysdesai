# Event-Driven Architecture(이벤트 기반 아키텍처)

> 출처: https://www.sysdesai.com/learn/architectural-styles/event-driven-architecture-style

---

## Event-Driven Architecture(EDA)란 무엇인가요?

**Event-Driven Architecture(EDA, 이벤트 기반 아키텍처)**는 시스템 내에서 발생한 사실인 **Events(이벤트)**의 생성, 탐지 및 소비를 중심으로 시스템을 구성하는 방식입니다. 구성 요소들이 서로를 직접 호출하는 방식(단단한 결합) 대신, 다른 구성 요소들이 독립적으로 구독할 수 있는 이벤트를 발행합니다. 이를 통해 생산자(Producer)와 소비자(Consumer)를 시간적, 공간적, 그리고 논리적으로 분리(Decouple)합니다.

Uber, LinkedIn, Airbnb와 같은 회사들은 이벤트 기반 시스템을 광범위하게 사용합니다. Uber의 운전자 위치 업데이트는 이벤트로 흐르고, LinkedIn의 피드 업데이트는 인맥으로부터 발생하는 이벤트이며, Airbnb의 예약 파이프라인은 검색부터 결제 확인까지 이벤트 기반으로 작동합니다.

## 핵심 구성 요소(Core Components)

이벤트 기반: 하나의 생산자, 여러 독립적인 소비자 — 브로커를 통해 모두 분리됨.

| 구성 요소 | 역할 | 예시 |
| --- | --- | --- |
| Event Producer | 자신의 도메인에서 일이 발생할 때 이벤트를 발행함 | 주문 서비스가 `order.placed` 발행, 결제 서비스가 `payment.processed` 발행 |
| Event Broker | 이벤트를 저장하고 구독자에게 라우팅함; 내구성과 재생 기능을 제공함 | Apache Kafka, AWS SNS/SQS, RabbitMQ, Azure Event Hubs |
| Event Consumer | 토픽을 구독하고 이벤트에 반응함 | 재고 서비스가 재고를 차감, 이메일 서비스가 확인 메일을 발송 |
| Event Schema | 이벤트 페이로드의 구조를 정의함 | 스키마 레지스트리에 저장된 Avro, Protobuf, JSON 스키마 |

## 이벤트 유형(Event Types)

모든 이벤트가 같은 것은 아닙니다. 다음 세 가지 패턴을 구분하는 것이 중요합니다:

- **Event Notification(이벤트 알림)**: 무언가 발생했음을 알리는 얇은(thin) 이벤트입니다. 소비자는 필요한 경우 세부 정보를 가져옵니다. 결합도는 낮지만 추가적인 왕복 통신이 필요합니다. 예: `{ type: 'order.placed', orderId: 'ord_123' }`.
- **Event-Carried State Transfer(이벤트 기반 상태 전송)**: 소비자가 필요로 하는 모든 데이터를 포함하여 콜백을 피합니다. 페이로드 크기는 커지지만 소비자는 완전히 자급자족할 수 있습니다. 예: `{ type: 'order.placed', orderId: 'ord_123', items: [...], total: 49.99 }`.
- **Event Sourcing(이벤트 소싱)**: 이벤트가 진실의 원천(Source of truth)이 됩니다. 데이터베이스에 현재 상태를 저장하는 대신, 전체 이벤트 시퀀스를 저장하고 이를 재생(Replay)하여 상태를 재구성합니다. 주로 금융 시스템에서 사용됩니다(모든 거래가 불변의 이벤트임).

## 코레오그래피 vs 오케스트레이션(Choreography vs Orchestration)

이벤트 기반 시스템에서 다단계 프로세스는 두 가지 방식으로 조정될 수 있습니다:

| 비교 항목 | Choreography(코레오그래피/안무) | Orchestration(오케스트레이션/지휘) |
| --- | --- | --- |
| 방식 | 각 서비스가 이벤트에 반응하고 새 이벤트를 발행함; 중앙 제어자 없음 | 중앙 오케스트레이터(Saga/Workflow)가 각 서비스에 할 일을 지시함 |
| 결합도 | 낮음 — 서비스들은 서로를 모름 | 보통 — 오케스트레이터가 모든 서비스를 알고 있음 |
| 가시성 | 서비스 전반에 걸친 전체 흐름을 추적하기 어려움 | 오케스트레이터가 프로세스의 단일 진실 원천이 됨 |
| 장애 처리 | 복잡함 — 보상 이벤트가 전파되어야 함 | 쉬움 — 오케스트레이터가 보상 단계를 관리함 |
| 예시 | 주문 발생 → 재고 반응 → 배송 → 알림 반응 | AWS Step Functions, Temporal, Netflix Conductor |

## 이벤트 기반 아키텍처의 장점

- **느슨한 시간적 결합(Loose temporal coupling)**: 생산자와 소비자가 동시에 활성 상태일 필요가 없습니다. 브로커가 이벤트를 버퍼링합니다.
- **쉬운 팬아웃(Fan-out)**: 생산자가 소비자를 전혀 모르는 상태에서 하나의 이벤트가 N개의 소비자를 트리거할 수 있습니다.
- **자동 감사 로그(Audit log)**: 로그 압축(Log compaction)이 적용된 Kafka나 이벤트 소싱을 사용하면, 발생한 모든 일에 대한 내구성 있고 재생 가능한 히스토리를 갖게 됩니다.
- **회복 탄력성(Resilience)**: 소비자가 실패했다가 복구되면, 중단된 지점부터 이벤트를 다시 재생할 수 있습니다(Kafka Consumer Offsets).
- **확장성(Scalability)**: 소비자는 자신의 처리 대기열(Backlog)에 따라 독립적으로 확장할 수 있습니다.

## 과제 및 트레이드오프

> ⚠️
> 최종 일관성(Eventual Consistency)
> EDA 시스템은 본질적으로 최종 일관성을 가집니다. 주문이 발생하면 재고 업데이트는 비동기적으로 이루어집니다. 즉, 주문은 완료되었지만 재고는 아직 차감되지 않은 짧은 시간이 존재합니다. 시스템은 이를 반드시 처리해야 합니다: 멱등성 소비자, 보상 트랜잭션, 그리고 최종 상태에 대한 명확한 사용자 메시징이 필요합니다.

- **이벤트 스키마 진화**: 소비자를 망가뜨리지 않고 스키마를 변경하려면 스키마 레지스트리와 하위/상위 호환성 전략이 필요합니다.
- **중복 이벤트**: At-least-once 전달 방식은 소비자가 동일한 이벤트를 두 번 받을 수 있음을 의미합니다. 모든 소비자는 반드시 **Idempotent(멱등성)**를 가져야 합니다.
- **순서 어긋남**: 이벤트가 순서대로 도착하지 않을 수 있습니다. 소비자는 이를 우아하게 처리하거나 순서가 보장된 파티셔닝을 사용해야 합니다.
- **분산 트레이싱**: 10개의 소비자로 팬아웃되는 사용자 요청을 디버깅하려면 상관관계 ID(Correlation ID)와 분산 트레이싱(Jaeger, OpenTelemetry)이 필수입니다.
- **디버깅 복잡성**: 선형적인 콜스택을 따라갈 수 없습니다. 흐름은 이벤트 구독에 의해 암시적으로 정의됩니다.
