# Peer-to-Peer Architecture(P2P 아키텍처)

> 출처: https://www.sysdesai.com/learn/architectural-styles/peer-to-peer

## Client-Server(클라이언트-서버) vs Peer-to-Peer(피어 투 피어)

전통적인 **Client-Server(클라이언트-서버)** 모델에서는 클라이언트가 리소스를 요청하고 서버가 이를 제공합니다. 서버는 항상 켜져 있고 중앙에서 관리되며 정본 데이터를 보유합니다. 이 모델은 단순하고 보안이 쉬우며 이해하기 쉽지만 병목 현상을 유발합니다. 서버에 장애가 발생하거나 부하가 걸리면 모든 클라이언트가 영향을 받습니다.

**Peer-to-Peer(P2P, 피어 투 피어)** 아키텍처에서는 모든 노드가 클라이언트이자 서버 역할을 동시에 수행합니다. 노드들은 중앙 조정자 없이 대역폭, 저장 공간, 컴퓨팅 리소스를 서로 직접 공유합니다. 이는 단일 장애 지점(SPOF)을 제거하고, 노드가 참여할 때마다 리소스가 함께 추가되므로 시스템 용량이 자동으로 성장할 수 있게 합니다.

클라이언트-서버(중앙 집중형) vs 피어 투 피어(분산형 메쉬 토폴로지).

## P2P 토폴로지 유형(P2P Topology Types)

| 토폴로지 | 설명 | 예시 |
| --- | --- | --- |
| Unstructured P2P(비구조적) | 피어들이 무작위로 연결됨; 플러딩(Flooding)이나 가십(Gossip)으로 탐색 | 초기 Gnutella, Freenet |
| Structured P2P(구조적, DHT) | 일관된 해시 링(Consistent hash ring)으로 피어 배치; 조회 속도 O(log N) | Chord, Kademlia (비트토렌트, IPFS에서 사용) |
| Hybrid P2P(하이브리드) | 탐색/조정을 위한 중앙 서버 존재; 데이터 전송은 피어 간 직접 수행 | 초기 Napster, 과거의 Skype |

## Distributed Hash Tables(DHT, 분산 해시 테이블)

**Distributed Hash Table(DHT, 분산 해시 테이블)**은 구조적 P2P를 가능하게 하는 핵심 데이터 구조입니다. 모든 노드에 분산된 키-값 조회 서비스를 제공합니다. 각 노드는 일정 범위의 키를 책임집니다. 키 조회는 O(log N)번의 홉(hop)을 거칩니다 (N은 노드 수). **Kademlia**는 비트토렌트의 피어 탐색과 IPFS를 구동하는 가장 널리 배포된 DHT입니다.

```javascript
// Kademlia DHT 조회 (단순화된 예시)
// 각 노드는 160비트 ID를 가짐. XOR 거리에 따라 라우팅 결정.

function lookup(targetKey) {
  candidates = kBucket.getClosestNodes(targetKey, k=20);

  while (true) {
    // 각 후보에게 "targetKey와 가장 가까운 노드를 아는가?" 질의
    newCandidates = mergeResults();
    if (noCloserNodesFound) {
      return closestKnownNodesToTargetKey;
    }
    candidates = newCandidates;
  }
}
// 매 홉마다 대상 노드에 더 가까워짐.
// N개의 노드가 있는 네트워크에서 O(log N)번의 홉 발생.
```

## Gossip Protocols(가십 프로토콜)

**Gossip protocols(가십 프로토콜)**(에피데믹 프로토콜이라고도 함)은 P2P 및 분산 시스템에서 정보를 전파하는 데 사용되는 통신 메커니즘입니다. 각 노드는 주기적으로 무작위 이웃 노드 세트를 선택하여 자신의 상태를 공유합니다. 마치 사람들 사이에 소문이 퍼지는 것처럼, 중앙 조정자 없이도 정보가 기하급수적으로 빠르게 전파됩니다. Cassandra는 클러스터 멤버십과 장애 탐색에 가십을 사용하며, AWS DynamoDB는 링 멤버십 관리에 이를 사용합니다.

## BitTorrent(비트토렌트): P2P 파일 배포

**BitTorrent(비트토렌트)**는 가장 성공적인 P2P 파일 배포 프로토콜입니다. 파일을 여러 조각(chunk)으로 나누고, 피어들은 여러 소스에서 동시에 조각들을 다운로드하며 자신이 가진 조각을 다른 이들에게 업로드합니다. 파일이 인기가 많아질수록 조각을 공유할 수 있는 피어가 많아지므로, 시스템의 대역폭은 수요에 따라 **증가**합니다 (수요가 많을수록 서비스 질이 떨어지는 클라이언트-서버 모델과 정반대).

Facebook의 P2P 배포 도구

Facebook(현재 Meta)은 배포 시 수십만 대의 서버에 OS 이미지와 애플리케이션 바이너리를 배포하기 위해 'BitTorrent on HDFS'(이후 'Conveyor')라는 비트토렌트 기반 내부 도구를 사용했습니다. 단일 파일 서버가 병목이 되는 대신 서버들이 서로 배포 패키지를 공유함으로써, 수 시간 걸리던 클러스터 전체 배포를 단 몇 분 만에 완료할 수 있었습니다.

## P2P 아키텍처로서의 블록체인(Blockchain as P2P Architecture)

**Blockchain(블록체인)**은 P2P 기반 위에 구축되었습니다. 비트코인이나 이더리움 네트워크의 모든 노드는 원장(ledger)의 전체 복사본을 보유합니다. 트랜잭션은 피어 네트워크를 통해 가십 방식으로 전파되며, 합의(Consensus - 작업 증명, 지분 증명 등)를 통해 중앙 권위자 없이 어떤 트랜잭션을 수락할지 결정합니다. 탈중앙화, 검열 저항성, 비잔틴 장애 허용(BFT)과 같은 아키텍처적 특성들은 P2P 기반 구조에서 직접적으로 비롯됩니다.

## P2P의 트레이드오프

| P2P 장점 | P2P 단점 |
| --- | --- |
| 단일 장애 지점(SPOF)이 없음 | 일관성(Consistency)을 유지하고 이해하기 복잡함 |
| 참여자가 많을수록 확장됨 (사용자가 늘수록 대역폭 증가) | 보안과 신뢰 확보가 어려움 (시빌 공격 등) |
| 검열과 중앙 통제에 강함 | 신뢰할 수 있는 콘텐츠 관리가 어려움 |
| 중앙 서버 운영 비용을 제거함 | 성능 예측이 어려움 (피어의 가용성과 품질에 의존) |
| 자가 치유(Self-healing) 네트워크 토폴로지 | 디버깅과 모니터링이 현저히 어려움 |

> 💡
> 인터뷰 팁
> P2P 아키텍처가 면접에서 주요 설계 선택지로 등장하는 경우는 드뭅니다(대부분의 운영 시스템은 클라이언트-서버를 사용함). 하지만 다음과 같은 경우에는 등장합니다: CDN 설계(피어 간 콘텐츠 캐싱 및 공유), 분산 데이터베이스 내부(Cassandra, Dynamo의 가십 프로토콜), 그리고 탈중앙화나 검열 저항성이 필요한 시스템에 대한 질문입니다. 핵심 개념들을 숙지하세요: 구조적 조회를 위한 DHT, 전파를 위한 가십 프로토콜, 그리고 탈중앙화와 일관성/제어 간의 근본적인 트레이드오프.
