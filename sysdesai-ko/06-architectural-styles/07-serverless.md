# Serverless Architecture(서버리스 아키텍처)

> 출처: https://www.sysdesai.com/learn/architectural-styles/serverless

---

## Serverless(서버리스)란 무엇인가요?

**Serverless(서버리스)**는 클라우드 제공업체가 서버 인프라를 동적으로 관리하는 클라우드 실행 모델입니다. 개발자는 함수나 애플리케이션 로직을 배포하고, 제공업체는 프로비저닝, 확장, 패치 및 과금을 처리합니다. 유휴 서버가 아닌 실제 소비된 컴퓨팅 시간에 대해서만 비용이 청구됩니다. '서버리스'라는 명칭은 다소 오해의 소지가 있습니다. 여전히 서버는 존재하지만, 개발자로부터 완전히 추상화되어 보이지 않을 뿐입니다.

서버리스는 두 가지 관련 개념을 포함합니다: **Functions-as-a-Service(FaaS, 서비스형 함수)**—이벤트에 의해 트리거되는 수명이 짧은 컴퓨팅 함수(AWS Lambda, Google Cloud Functions, Azure Functions)—와 **Backend-as-a-Service(BaaS, 서비스형 백엔드)**—백엔드 구성 요소 전체를 대체하는 관리형 서비스(인증을 위한 Auth0, 실시간 DB를 위한 Firebase, 데이터베이스를 위한 AWS DynamoDB)입니다.

서버리스 패턴: API Gateway가 Lambda 함수로 라우팅하며, 관리형 서비스가 데이터와 메시징을 처리함.

## 주요 특징(Key Characteristics)

| 특징 | 상세 내용 |
| --- | --- |
| 서버 관리 불필요 | 제공업체가 OS, 런타임 업데이트, 보안 패치, 용량 계획을 처리함 |
| 실행당 과금 | 호출 횟수 및 컴퓨팅 사용량(GB-초)에 따라 과금 (유휴 시간 제외) |
| 자동 확장 | 0에서 수천 개의 동시 실행까지 자동으로 확장됨 |
| 이벤트 트리거 방식 | HTTP 요청, 큐 메시지, 파일 업로드, 예약된 타이머 등의 이벤트에 의해 호출됨 |
| 무상태성(Stateless) | 각 호출은 독립적임; 상태는 외부(DynamoDB, Redis, S3 등)에 저장해야 함 |
| 실행 제한 | AWS Lambda 기준: 최대 15분, 10GB 메모리, 512MB~10GB 임시 스토리지 |

## 콜드 스타트(Cold Starts)

FaaS의 가장 중요한 성능 특성은 **Cold start(콜드 스타트)**입니다. 함수가 최근에 호출되지 않았다면, 제공업체는 새로운 실행 환경을 구성해야 합니다(함수 패키지 다운로드, 런타임 초기화, 전역/모듈 레코드 코드 실행). 이로 인해 Node.js나 Python의 경우 약 100ms, Java나 Scala 같은 JVM 기반 런타임의 경우 수 초의 지연 시간이 추가됩니다.

> ℹ️
> 콜드 스타트 완화 전략
> 1. 몇 분마다 함수를 호출하는 'Warm-up' 예약 핑(ping)을 사용합니다. 2. AWS Lambda의 Provisioned Concurrency(예약된 동시성)를 활성화합니다(유휴 시에도 비용이 발생하지만 N개의 인스턴스를 항상 활성 상태로 유지). 3. Java/Kotlin보다 시작이 빠른 가벼운 런타임(Node.js, Python)을 선택합니다. 4. 함수 패키지 크기를 최소화하고 전역 범위에서의 무거운 초기화 작업을 피합니다.

## 서버리스가 적합한 경우

- **예측 불가능하거나 급증하는 트래픽**: 새벽 3시에는 요청이 0건이고 반짝 세일 기간에 50,000건의 요청을 처리하는 함수의 경우, 새벽 3시에는 비용이 전혀 발생하지 않습니다.
- **이벤트 기반 파이프라인**: S3 파일 업로드 시 이미지 크기 조정, CloudWatch 로그 처리, 야간 데이터 엑스포트 등 트리거 기반의 짧은 작업에 완벽하게 어울립니다.
- **빠른 프로토타이핑 및 MVP**: 인프라 설정 없이 비즈니스 로직에만 집중할 수 있습니다.
- **호출 빈도가 낮은 마이크로서비스**: 드물게 호출되는 함수를 위해 서버를 계속 띄워 리소스를 낭비할 필요가 없습니다.
- **웹훅 핸들러(Webhook handlers)**: 외부 웹훅 엔드포인트(Stripe 결제 이벤트, GitHub 웹훅 등)는 Lambda의 이상적인 유스케이스입니다.

## 서버리스가 적합하지 않은 경우

- **오래 걸리는 프로세스**: Lambda의 15분 제한 때문에 비디오 인코딩, ML 학습, 또는 수 시간이 걸리는 ETL 작업에는 적합하지 않습니다.
- **지연 시간에 민감한 실시간 시스템**: 콜드 스타트로 인해 예측 불가능한 지연 시간 스파이크가 발생할 수 있어, 100ms 미만의 SLA가 필요한 환경에는 부적합합니다.
- **처리량이 높고 일정한 부하**: 요청 속도가 지속적으로 높을 경우, 실행당 과금 방식이 전용 EC2 인스턴스를 운영하는 비용보다 비싸질 수 있습니다.
- **상태 유지 프로토콜**: WebSockets과 같은 수명이 긴 연결은 처리하기 까다롭습니다(AWS API Gateway의 WebSocket 지원이나 별도의 WebSocket 서버가 필요).
- **벤더 종속성(Vendor lock-in)**: 특정 클라우드 전용 트리거(S3 이벤트, DynamoDB 스트림 등)에 묶인 Lambda 함수는 다른 클라우드로 옮기기 어렵습니다.

## 비용 모델 비교(Cost Model Comparison)

📌
손익분기점 예시

AWS Lambda 비용은 약 100만 회 호출당 0.20달러 + GB-초당 0.0000166667달러입니다. 512MB 메모리로 200ms 동안 실행되는 함수는 호출당 0.0000016667달러입니다. 월 1,000만 회 호출 시 약 18.67달러가 듭니다. 반면 100% 가동되는 t3.medium EC2(시간당 0.0416달러)는 월 약 30달러입니다. 월 1,000만 회 요청까지는 서버리스가 저렴하지만, 월 5억 회 요청 수준이 되면 전용 인스턴스 그룹이 훨씬 저렴해집니다.

> 💡
> 인터뷰 팁
> 시스템 디자인 면접에서 이벤트 기반 트리거(파일 업로드, 큐 메시지), 급증하는 트래픽, 또는 운영 오버헤드 최소화가 필요할 때 서버리스를 언급하세요. 반드시 한계점도 함께 짚어주어야 합니다: 지연 시간에 민감한 경로에서의 콜드 스타트, 긴 작업에 대한 실행 시간 제한, 그리고 지속적으로 높은 처리량 발생 시의 비용 문제 등을 언급하세요. 이러한 트레이드오프 인식 능력이 뛰어난 후보자를 가르는 기준이 됩니다.
