# Monolith vs Microservices(모놀리스 vs 마이크로서비스)

> 출처: https://www.sysdesai.com/learn/architectural-styles/monolith-vs-microservices

---

## 기초적인 선택(The Foundational Choice)

모든 시스템은 어디선가 시작됩니다. 코드를 한 줄도 쓰기 전에 내리는 첫 번째 주요 아키텍처 결정은 **Monolith(모놀리스)**로 구축할지 아니면 **Microservices(마이크로서비스)** 시스템으로 구축할지 여부입니다. 이 선택은 팀 구조, 배포 전략, 운영 복잡성 및 장기적인 개발 속도에 큰 영향을 미칩니다. 잘못된 선택은 큰 비용을 초래하지만, 트레이드오프를 이해하면 상황에 맞는 올바른 결정을 내릴 수 있습니다.

## Monolith(모놀리스)란 무엇인가요?

**Monolith(모놀리스)**는 모든 애플리케이션 기능이 포함된 단일 배포 단위입니다. UI 계층, 비즈니스 로직 및 데이터 액세스 코드가 함께 패키징되어 배포됩니다. 시스템의 어느 한 부분이라도 변경 사항을 푸시하면 전체를 다시 배포해야 합니다. Shopify, Stack Overflow, GitHub와 같은 초기 단계의 회사들은 거대한 모놀리스를 성공적으로 운영했으며, 일부는 현재도 운영하고 있습니다.

모놀리스: 모든 계층이 단일 배포 프로세스 내에서 실행됨.

### Monolith(모놀리스)의 장점

- **개발의 단순함**: 하나의 코드베이스, 하나의 IDE, 하나의 디버거만 있으면 됩니다. 내부 구성 요소 간의 네트워크 호출이 없습니다.
- **E2E(End-to-End) 테스트 용이**: 모든 구성 요소가 프로세스 내에 있으므로, 통합 테스트를 위해 여러 서비스를 띄울 필요가 없습니다.
- **낮은 운영 오버헤드**: 배포, 모니터링 및 확장해야 할 서비스가 하나뿐입니다.
- **분산 시스템 문제 없음**: 부분적 장애, 구성 요소 간의 네트워크 파티션, 최종 일관성(Eventual consistency) 문제 등이 없습니다.
- **강한 일관성(Strong consistency)**: 모든 비즈니스 로직이 하나의 데이터베이스 트랜잭션 경계를 공유합니다.

### Monolith(모놀리스)의 단점

- **확장 단위가 큼(Coarse-grained scaling)**: 이미지 처리 구성 요소만 부하를 받더라도 애플리케이션 전체를 확장해야 합니다.
- **배포 결합(Deployment coupling)**: 결제 모듈의 버그가 사용자 프로필 기능의 배포를 가로막을 수 있습니다.
- **기술 종속(Technology lock-in)**: 전체 코드베이스가 동일한 언어, 프레임워크 및 런타임 버전을 사용해야 합니다.
- **조직적 마찰**: 팀이 커짐에 따라 머지 충돌과 조정 비용이 증가합니다.
- **시작 시간**: 거대한 모놀리스는 부팅하는 데 수분이 걸릴 수 있어 개발 피드백 루프가 느려집니다.

## Microservices(마이크로서비스)란 무엇인가요?

**Microservices(마이크로서비스)**는 애플리케이션을 작고 독립적으로 배포 가능한 서비스들로 분해하며, 각 서비스는 제한된 도메인(Bounded domain)을 소유합니다. Amazon, Netflix, Uber가 이 스타일을 대규모로 개척했습니다. 각 서비스는 자체 프로세스와 데이터베이스를 가지며, 네트워크(주로 HTTP/REST, gRPC 또는 메시지 브로커)를 통해 다른 서비스와 통신합니다.

마이크로서비스: 각 서비스가 자신의 도메인과 데이터베이스를 소유하며, API나 이벤트를 통해 통신함.

### Microservices(마이크로서비스)의 장점

- **독립적 배포 가능성**: 팀들이 다른 팀과 조율하지 않고도 자신의 서비스를 배포할 수 있습니다.
- **세밀한 확장(Fine-grained scaling)**: 병목 현상이 발생하는 서비스만 확장할 수 있습니다(예: 트래픽 피크 시 추천 서비스의 레플리카만 추가).
- **기술 다양성**: 각 서비스는 해당 작업에 가장 적합한 언어나 데이터베이스를 선택할 수 있습니다.
- **장애 격리(Fault isolation)**: 알림 서비스의 장애가 주문 서비스까지 중단시키지 않습니다.
- **팀 자율성**: 콘웨이의 법칙(Conway's Law)이 유리하게 작용합니다. 작은 팀이 작은 서비스를 엔드 투 엔드로 소유합니다.

### Microservices(마이크로서비스)의 단점

- **분산 시스템의 복잡성**: 네트워크 호출 실패, 서비스 불능, 지연 시간 급증 등의 문제가 발생합니다. 재시도, 타임아웃, 서킷 브레이커 등을 직접 처리해야 합니다.
- **데이터 일관성**: 서비스 간 트랜잭션에는 Saga 패턴이나 최종 일관성 패턴이 필요합니다. 분산 ACID 트랜잭션은 존재하지 않습니다.
- **운영 오버헤드**: 수십 개의 서비스에는 Service Discovery(서비스 디스커버리), 로드 밸런싱, 중앙 집중식 로깅, 분산 트레이싱 및 Service Mesh(서비스 메쉬)가 필요합니다.
- **통합 테스트의 어려움**: 로컬에 유사한 환경을 구축하려면 오케스트레이션(Docker Compose, Kubernetes)이 필요합니다.
- **지연 시간(Latency)**: 이전에는 프로세스 내 함수 호출이었던 것이 이제는 직렬화 오버헤드가 있는 네트워크 홉이 됩니다.

## 정면 비교(Head-to-Head Comparison)

| 비교 항목 | Monolith(모놀리스) | Microservices(마이크로서비스) |
| --- | --- | --- |
| 배포 | 단일 아티팩트 | 서비스별 아티팩트 |
| 확장 | 앱 전체 확장 | 서비스별 개별 확장 |
| 팀 구조 | 코드베이스 공유 | 서비스별 팀 구성 |
| 데이터 관리 | 데이터베이스 공유 | 서비스별 데이터베이스 |
| 장애 격리 | 낮음 — 하나가 죽으면 전체 중단 | 높음 — 결함이 격리됨 |
| 운영 복잡성 | 낮음 | 높음 |
| 일관성 | 강한 일관성 (ACID) | 최종 일관성 (Saga/Outbox) |
| 최적의 용도 | 초기 단계, 소규모 팀 | 대규모 조직, 자율성 필요 시 |

## 선택 기준

> 💡
> 모놀리스로 시작하세요.
> 마틴 파울러(Martin Fowler)의 조언은 여전히 유효합니다: 잘 구조화된 모놀리스('Modular monolith')로 시작하십시오. 마이크로서비스는 확장이 명확하게 필요하거나 팀 자율성 문제가 발생했을 때 도입해야지, 기본 시작점으로 삼아서는 안 됩니다. Amazon, Shopify, GitHub 모두 성공적인 모놀리스를 먼저 구축했습니다.

다음과 같은 경우 **Monolith(모놀리스)**를 선택하세요: 도메인이 아직 명확하지 않을 때, 팀 규모가 작을 때(~15명 미만), 독립적 확장성보다 배포 속도가 더 중요할 때, 또는 MVP를 구축할 때.

다음과 같은 경우 **Microservices(마이크로서비스)**를 선택하세요: 도메인별로 명확한 확장 요구사항이 있을 때, 독립적으로 배포해야 하는 여러 팀이 있을 때, 장애 격리가 필요한 높은 신뢰성 예산이 있을 때, 또는 서비스 경계가 명확한 외부 서비스와 통합할 때.

## 마이그레이션: 모놀리스에서 마이크로서비스로

**Strangler Fig pattern(스트랭글러 피그 패턴)**(기존 나무를 감싸며 자라 결국 대체하는 무화과나무의 이름을 딴 패턴)이 표준 마이그레이션 방식입니다. 기존 모놀리스가 나머지를 처리하는 동안 특정 요청 경로를 새 마이크로서비스로 라우팅합니다. 시간이 지나면서 서비스가 모놀리스의 책임을 흡수함에 따라 모놀리스를 점진적으로 대체해 나갑니다.

```javascript
// Strangler Fig — API Gateway 라우팅 규칙 (의사 코드)

function route(request) {
  if (request.path.startsWith("/payments")) {
    forwardTo(PaymentsMicroservice);
  } else if (request.path.startsWith("/recommendations")) {
    forwardTo(RecommendationsMicroservice);
  } else {
    forwardTo(LegacyMonolith); // 나머지는 여전히 모놀리스가 처리
  }
}
```

> ⚠️
> 'Distributed Monolith(분산 모놀리스)' 안티 패턴을 피하세요.
> 최악의 결과는 분산 모놀리스입니다: 코드베이스는 별도의 서비스로 나누었지만, 단일 데이터베이스를 공유하고 공동 배포가 필요한 경우입니다. 마이크로서비스의 비용은 모두 지불하면서 이점은 하나도 얻지 못하게 됩니다. 핵심 규칙: 각 서비스는 자신의 데이터를 소유해야 합니다.
